# K3 spec · City hubs

Just-in-time spec for stage K3 of Kanāli ([ledger](kanali.md#feature-ledger), K-71), written 11 Nov 2026 against `main` at `1d4e9a7`. Drawing: [`docs/development/kanali/hub.html`](../kanali/hub.html) v18, sections `board-city`, `drop-kur`, `request-sheet`, `city-hub`, `page-overview` (read the source by function, never the whole file; line numbers are v18). The ledger row wins over the drawing; the drawing wins over this spec except where this spec names an owner question. K1 and K2 are built ([K1.md](K1.md), [K2.md](K2.md)): this spec only names what changes.

**Scope:** the two kinds of city hub decided on 11 Nov (K-125..K-130). The **city hub** "Kopiena Jelgava" (`/lv/jelgava`, K-57, K-10): one per city on the site's list, all Veidi inside, read-only Ziņas, Pilsētas istabas list. The **topic × city hub** ("Galda spēles › Šahs › Jelgava"): opens on request (first "Pieprasīt" with an optional public Ziņa, the second request opens it at once, site admins can close it, K-09a). Kur on a topic hub becomes a **switcher** to topic × city hubs (K-127; K-09b Changed). The board's hub card pairs the topic hub with the city hub when Kur is one city (K-130, `board-city`).

**Not in K3:** chat rooms and Matrix (K4/K5; what K5 needs is listed in section 9), districts (K-11), hub admins other than site admins (K-38c), a city-only hub card on the board without a Veids (design.md keeps "never with a Tēma alone"), a rooms Katalogs (K-88, K5).

**Data: one additive migration** `hub_cities`: two tables, one enum. Nothing renamed or dropped. The city hub itself is **derived** from `City` (every `ACTIVE` city is a city hub), so "precreated for every city, created when a city is added" holds with no rows to keep in sync: `CityService.createActive` and `approve` make the hub exist.

**Size and split: three builder sessions**, each one commit set, each reviewed on its own, run in order.

## Invariants (all sessions; the reviewer checks each)

- Every screen outside the ones listed under Visual baseline renders pixel-identical. The four K1/K2 hub screens (`hub-overview`, `hub-groups`, `hub-events`, `hub-notes`) show **no diff**: the closed Kur button still reads "Kur: Visas pilsētas".
- No Prisma outside `lib/services/`; hub pages read one `HubContext` via `useHubContext()`, city hub pages one `CityHubContext` via `useCityHubContext()`; `--accent` is set server-side in the layout (Taxonomy Law). No page reads the city from `searchParams` any more: the city is part of the address and of the context.
- **One request per person per topic × city**; the second **distinct** person opens it, exactly once, under a lock (two parallel second requests open one hub and send one set of notifications).
- **Nobody writes on the city hub**: no compose, reply, Rakstīt privāti or Ziņot control renders there, and no action accepts a city hub as a note target (notes always belong to a topic hub, `HubNote.categoryId`).
- **Signed out gets no names** (K2 invariant): city hub Ziņas rows come from the same service path with `author: null`; request counts are numbers, never names.
- A topic × city hub that is not `OPEN` is reachable by no page: its address redirects (K3-08), and it appears in no Pilsētas istabas list or hub card.
- Every mutation returns `ActionResponse<T>`, has a submission guard, validates with shared Zod schemas; no hard-coded strings; `lv.json` and `en.json` change together; no new docs besides this spec.

## Motivation and design alignment

Places matter as much as topics for meeting in person (K-70, Jelgava pilot). A city is a parallel dimension (K-08): the city hub gathers everything in Jelgava, the topic × city hub is where Šahs people in Jelgava find each other. Both reuse the hub frame, rows, tiers and queries from K1/K2: every K1/K2 query already takes `cities: string[]`, so a topic × city hub is a topic hub with one city fixed in its context, and a city hub is the same activity and note queries with the topic removed (Service Law: `HubCityService` and `CityHubService` own the new reads and writes; the Context Law keeps the city in `HubContext`, never prop-drilled). Requests replace an approval queue with a social signal (two people want it → it exists), cheap for a site without moderators (K-38c), and the optional note doubles as the first Ziņa (K-18a).

## 2. Data (K3-1)

### 2.1 Migration `hub_cities` — K3-01

`npm run db:migrate -- --name hub_cities`. Additive; back-relations on `Category`, `City`, `User`, `HubNote`.

```prisma
enum HubCityStatus { REQUESTED OPEN CLOSED }

model HubCity {                    // a topic × city hub ("Šahs · Jelgava")
  id         String        @id @default(cuid())
  categoryId String                // the topic hub: an ACTIVE L2 or L3 Category
  cityId     String                // an ACTIVE City
  status     HubCityStatus @default(REQUESTED)
  openedAt   DateTime?
  closedAt   DateTime?
  closedById String?
  createdAt  DateTime      @default(now())
  updatedAt  DateTime      @updatedAt
  // category Cascade, city Cascade, closedBy (User) SetNull
  requests   HubCityRequest[]
  @@unique([categoryId, cityId])
  @@index([cityId, status])
}

model HubCityRequest {             // one "Pieprasīt"
  id        String   @id @default(cuid())
  hubCityId String
  userId    String
  noteId    String?  @unique        // the optional note, a HubNote (K-18a); SetNull
  createdAt DateTime @default(now())
  // hubCity Cascade, user Cascade, note SetNull
  @@unique([hubCityId, userId])
}
```

No column for a chat room yet: K5 adds it (section 9).

### 2.2 Constants and validation — K3-02

`lib/constants/hubs.ts`: `HUB_CITY_OPEN_AT = 2` (distinct requesters that open a hub, K-09a), `CITY_RESERVED_SEGMENTS` = every static folder under `app/[locale]/` (`about`, `admin`, `auth`, `create`, `email`, `onboarding`, `privacy`, `profile`, `messages`, `notifications`, `settings`, `group`) plus `HUB_RESERVED_SLUGS`. Beside the K2 note schema in `lib/validations/`: `hubCityRequestSchema` `{ hubSlug, city, note? }` where `note` reuses the K2 note content rule (≤ `HUB_NOTE_MAX`, trimmed, empty → undefined), and `hubCityCloseSchema` `{ hubCityId }`. Error codes in `types/actions.ts`: `HUB_CITY_REQUESTED` (viewer already asked). Unknown city or hub → `NOT_FOUND`; a note over the limit → K2's `HUB_NOTE_LIMIT`.

## 3. Addresses and slugs (K3-1)

### 3.1 City segment — K3-03

`City.slug` is stored capitalised (`Jelgava`, `Riga`, `Jekabpils`, `city.service.ts` `citySlugBase` l.39); the address segment is `slug.toLowerCase()` (`/lv/jelgava`, `/lv/riga`). `CityService.bySegment(segment, locale)` (cached with the existing `CITIES_TAG`) returns the `ACTIVE` city whose lower-cased slug matches, else null; `PENDING_REVIEW` cities have no hub. The board's `?city=Jelgava` keeps the stored slug (no change to `lib/discovery-params.ts`).

**Slug guards.** Static folders under `app/[locale]/` already win over `[l1Slug]`, so the guards keep segments unambiguous:
- `CityService.suggest` and `createActive`: a base whose lower case is in `CITY_RESERVED_SEGMENTS` or equals an L1 slug counts as taken, so the existing attempt loop gives `Admin-2` (l.~194 and l.~231, the `attempt` loops).
- `taxonomy.service.ts` (L1/L2/L3 create, rename, merge targets) refuses a slug equal to an `ACTIVE` city segment with the existing slug-taken error. The seed has no collision (cities `riga`…`valmiera`, L1s `games`, `sports`, `social`, …): the builder confirms with one query.
- Resolution order wherever a segment could be both: **category first**, city second.

### 3.2 Paths — K3-04

`lib/hub-path.ts` (pure): `parseHubPath` returns `{ l2Slug, middle: string[] (0..2), page }` for `[l2, …middle, page?]` with `page ∈ HUB_PAGE_KEYS`; anything longer is null. `HubService.getHubContext(l1, l2, middle, locale)` resolves `middle`: `[l3]`, `[city]`, `[l3, city]`, where a segment is an L3 child of the L2 first, else a city segment (3.1); anything else → `notFound()`. `hubHref(l1, l2, l3?, page?, citySegment?)` gives `/games/boardgames/chess/jelgava/events`. Topic × city addresses: `/lv/games/boardgames/jelgava`, `/lv/games/boardgames/chess/jelgava/messages`. A path, not `?city=`, because the head (title, stats) is rendered in the layout and layouts get no `searchParams`.

## 4. Service and actions (K3-1)

### 4.1 `lib/services/hub-city.service.ts` (new, ≤ 150) — K3-05..K3-07

- **`kurOptions(hub, viewerId?)`** — K3-06. For the Kur switcher: every `ACTIVE` city with `{ segment, name, status: 'open' | 'requested' | 'none', groupCount, requestCount, viewerRequested }`. `groupCount` from the existing `hubCityCounts` (`hub-query.ts` l.33). Order: open first by `groupCount` desc, then the rest by name (`Intl.Collator` for the locale, as `CityService` sorts today). `CLOSED` reads as `none`.
- **`request({ hub, citySegment, userId, note? })`** — K3-05. One transaction: `pg_advisory_xact_lock(hashtext('hub-city:' || categoryId || ':' || cityId))`; upsert the `HubCity` (a `CLOSED` row goes back to `REQUESTED`); if the viewer already has a request → `ActionError('HUB_CITY_REQUESTED')`; if the row is `OPEN` → return `{ opened: true }` without a request; with a note, create it through K2's note path **inside the same transaction** (export a `createNoteTx(tx, …)` from `hub-note.service.ts` so `lockAuthor` and `assertRoom` run as in K2; the note is `categoryId` = the topic hub, `cityId` = the city, no group, K-116/K-117); create the request; when distinct requesters reach `HUB_CITY_OPEN_AT`, set `OPEN`, `openedAt`. Returns `{ opened: boolean, href, notifyUserIds }` (the earlier requesters when it opened). A note over the limit aborts the whole request (`HUB_NOTE_LIMIT`; the sheet says so and keeps the text, K3-11).
- **`close(hubCityId, adminId)`** — K3-05. Site admin only (checked again in the service). `OPEN` → `CLOSED`, `closedAt`, `closedById`; deletes its `HubCityRequest` rows (notes stay: they are plain Ziņas); writes an `AdminAction` (`HUB_CITY_CLOSE`, `targetName` "Šahs · Jelgava"). Reopening needs two new requests.
- **`openInCity(cityId, locale)`** — for K3-2's Pilsētas istabas and K3-3's card: `OPEN` rows with the topic's localized `title`, L1/L2 slugs for the href, group count in that city and last activity (`max(Group.updatedAt / Event.createdAt)` as the K1 card does for "Pēdējā aktivitāte"; the builder reuses whichever helper `hub-summary.ts` uses).
- **`statusOf(categoryId, cityId)`** — for the resolver (K3-08).

### 4.2 Actions `actions/hub-city-actions.ts` (new, ≤ 90) — K3-07

`requestHubCity` (auth → `UNAUTHORIZED`; parse; `HubCityService.request`; `revalidatePath` of the topic hub layout; on `opened` notify `notifyUserIds` with `HUB_CITY_OPENED`, link = the new hub's href) and `closeHubCity` (`requireSiteAdmin()`; revalidate topic hub, topic × city hub, city hub). No admin notification on open (K-09a, 10 Nov: no approval step).

### 4.3 Notifications — K3-13

New type `HUB_CITY_OPENED` beside `HUB_NOTE_REPLY` (types list, icon `MapPin`, `lib/constants/email.ts` digest list as K2 did), text with `{hubName}` and `{cityName}`.

### 4.4 Tag merges — K3-14

`HubCity.category` cascades: `mergePendingTag` (l.484), `mergeL2` (l.501), `bulkMerge` (l.941) in `taxonomy.service.ts` move `HubCity` rows to the canonical id in the same transaction as K2's note move. On a `(categoryId, cityId)` clash keep the more advanced row (`OPEN` > `REQUESTED` > `CLOSED`), move the other's requests to it (skipping duplicate users), delete the other.

## 15. Risks

1. **Segment ambiguity.** `/lv/<x>` and `…/<l2>/<x>` can be a category or a city. Category-first resolution plus guards in both directions; an L3 slug equal to a city segment under the same L2 would hide that topic × city hub (accepted: hobby slugs and town names don't overlap; the guard blocks new ones).
2. **Removing `?city=`.** K1/K2 pages read it in several places (`lib/hub-pages.ts`, `HubPlaceButton`, page components, notes Kur); a missed read silently shows nationwide data on a topic × city hub. Grep `cities` and `searchParams` in `components/hubs` and `app/[locale]/[l1Slug]`.
3. **Open race.** Without the lock two second requests can both see one request and both open (two notifications, or a unique-violation crash on the request).
4. **Cascades.** `HubCity.city` cascades: `CityService.reject` only touches `PENDING_REVIEW` cities, which never have rows; if a city delete is ever added it removes its topic × city hubs (notes keep `cityId` SetNull from K2).
5. **Drawing drift.** `drop-kur` (`ddInner`) still shows "Jelgava · Jelgavas kopiena" as a Kur row; K-127 wins. The drawing needs one update by the owner's drawing agent (not part of this build).
