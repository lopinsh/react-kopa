# K1 spec · Hub pages without chat

Just-in-time spec for stage K1 of Kanāli ([ledger](kanali.md#feature-ledger), K-71), written 10 Nov 2026 against `main` at `166e2e4`. Drawing: [`docs/development/kanali/hub.html`](../kanali/hub.html) v18 (read its source by function, never the whole file; line numbers below are v18). The ledger row wins over the drawing; the drawing wins over this spec where they disagree, except where this spec names an owner question.

**Scope:** a hub page for every active Veids (L2) and sub-veids (L3), built in the group-page frame, with Pārskats, Grupas and Pasākumi; the hub card on the board; the group page's category line linking to hubs. Built only from **Confirmed** ledger rows.

**Not in K1:** Ziņas / shout-outs data (K2: K-26, K-27, K-27a, K-77, K-83, K-111), city hubs and "Pieprasīt" (K3: K-08, K-09a, K-10, K-18a), Matrix and Čats (K4, K5: K-30..K-38c, K-80..K-88, K-101), blog posts (K-24 own release; K1 shows no "raksti"), moderation (K-42), districts (K-11).

**Data: no migration** (K-71). A hub is derived, never stored: its groups are the PUBLIC, unhidden groups tagged with that Veids or one of its L3 children ([code survey](kanali.md#facts-from-the-code-survey)); its events and announcements are those groups' `PUBLIC` ones. The seed is unchanged (see Visual baseline).

**Size and split: four builder sessions**, each one commit set, each reviewed on its own; K1-2..K1-4 depend on K1-1 only and may run in any order.

| Session | What | Rule ids |
|---|---|---|
| **K1-1** · Frame, service, Grupas, group links | `HubService`, routes, layout (head, menu, Kur, sticky bar, drawer), Grupas page, K-50 | K1-01..K1-12 |
| **K1-2** · Pasākumi | Day strip, quiet and busy month, Gaidāmie / Pagājušie, desktop card grid | K1-13..K1-18 |
| **K1-3** · Pārskats and signed out | Activity feed, Pasākumi and Grupas previews, sub-veidi chips, desktop panel grid, signed-out view | K1-19..K1-25 |
| **K1-4** · Board hub card | One card first in the grid: one, parent + child, siblings, 3+ | K1-26..K1-30 |

## Invariants (all sessions; the reviewer checks each)

- The board without a Veids filter, the group pages, the event page, the panels and Ziņas inbox render pixel-identical (visual baseline; only the screens listed under Visual baseline may change).
- `discoveryHref`, `parseDiscoveryParams` and `topicHref` return exactly today's strings for every board call (the new `path` field defaults to the board).
- Group routes `/[l1Slug]/group/[groupSlug]/**` and the `@panel` interception keep working: a soft navigation board → group still opens the panel; board → hub opens the full hub page with no panel.
- No Prisma outside `lib/services/`; hub pages read one `HubContext` through `HubProvider` / `useHubContext()` (Context Law); `--accent` set server-side in the hub layout from the L1 (Taxonomy Law).
- Nothing members-only ever reaches a hub: only `Visibility.PUBLIC` events and posts of PUBLIC, unhidden groups; archived announcements excluded.
- No new docs besides this spec; no hard-coded strings; `lv.json` and `en.json` change together.

## Motivation and design alignment

A hub is the town square of one Veids (K-05, K-39): people who will not create a group still find what is happening around their interest. It reuses the group frame (layout B, AR-47) so the site has one way to show "a place with pages", and it reuses discovery's queries and parts (cards, rows, day strip, Kur list) so a hub shows the same things the board does, only gathered. Everything is read from existing rows (Service Law: one `HubService`), so the stage ships without a migration and without new moderation load.

## 2. Data and service (K1-1)

### 2.1 `lib/services/hub.service.ts` (new, ≤ 150 lines) + `lib/services/hub-query.ts` (new, ≤ 120)

- **K1-01** `HubService.getHubContext(l1Slug, l2Slug, l3Slug | undefined, locale, viewerId?) → HubContext | null`. Resolves the chain by `Category.slug` (the same global slug the board and group URLs use), requires `status ACTIVE`, L1 → L2 (→ L3) parentage, else `null` → `notFound()`. Returns: `id`, `level` (2 | 3), `slug`, `title` (localized, `TaxonomyResolver`), `name` (the hub name, K1-02), `path` (`[{ title, href }]`: L1 → `topicHref(l1)` on the board (L1 has no hub, K-06/K-29), L2 → its hub; the last part is the current hub, not a link), `theme.accentColor` (from `TaxonomyResolver`, as `GroupService.getGroupWithContext`), `stats { memberCount, groupCount }` (K-76: distinct users with a membership in the hub's groups; members of two groups count once), `subTopics [{ slug, title, href, groupCount }]` (L3 children of an L2 hub, by group count desc; empty on an L3 hub), `pages` (K1-04), `viewer { signedIn }`.
- **K1-02** Hub name (K-01a) "<tēma> kopiena" needs the Latvian genitive ("Galda spēļu kopiena", "Šaha kopiena"), which the taxonomy does not store. Default without a migration: `lib/constants/hub-names.ts` maps category slug → LV genitive for the current L2/L3 slugs; the service falls back to `hub.nameFallback` ("Kopiena: {title}") for a slug not in the map; EN is always `hub.name` ("{title} community"). Owner question 1.
- `hubGroupWhere(hub, cities)` in `hub-query.ts`: reuse `groupWhere` from `discovery-query.ts` with `categoryId` = the L1 and `tags: [hub.slug]` (its `anyTopic` already matches L3 children of an L2). One where-clause feeds groups, events, posts and counts, so a hub never shows a group the board would not.
- `HubService.getGroups(hub, { cities, tab, take }, locale, viewerId?) → { groups: GroupCardData[], total, activity, faces, myRoles }`: `GROUP_CARD_SELECT`, the board's order; `tab 'new'` = created in the last 30 days (`HUB_NEW_DAYS`). Reuse the board's activity, faces and role loaders (`card-activity.ts`, `card-faces.ts`, `my-groups.ts`), not copies.
- `HubService.getSummary(slugs[], locale)` (K1-4 uses it): per hub `name`, `href`, `stats`, `nextEvent { title, startsAt } | null`, `lastActivityAt | null` (newest of group created, member joined, public post, public event created), `subTopics` (top 3 + `moreCount`). One query per source for all slugs, no N+1.
- Events and the feed are added by K1-2 and K1-3 to the same service (2.2, 5.1).

## 13. Risks

1. **Parallel route on soft navigation.** The `@panel/(.)[l1Slug]` interception lives under the same L1 segment; a board → hub link could render the slot's layout or 404 the page. Check with a client navigation first thing in K1-1 commit 2; if the slot misbehaves, add `@panel/(.)[l1Slug]/[...hub]/page.tsx` returning `null` (read `node_modules/next/dist/docs/` on parallel and intercepting routes).
2. **Slug collisions.** An L2/L3 slug equal to `groups` or `events` would shadow a hub page; reserved slugs guard new ones, the reviewer checks existing ones on production with a read-only query (a collision blocks the push, the owner renames).
3. **Query cost.** Distinct member counts across groups and the feed's counts run per request; keep them in `unstable_cache` with the board's tags/revalidation, or plain queries with `@@index([groupId, …])` already present; no N+1 in `getSummary`.
4. **Pārskats has no tab bar in K1.** The approved drawing's Pārskats tab row (jumps to sections, K-86 note on `page-overview`) only holds what Ziņas adds; default: no tab row on Pārskats in K1, the content starts under the head (K-110).
5. **DiscoveryParams `path`.** Touches every board link; commit 1 of K1-2 must leave all baselines identical.
