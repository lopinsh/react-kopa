# L3 spec · Sub-veidi and category images

Just-in-time spec for Kanāli stage L3 ([ledger](kanali.md#feature-ledger) K-05, K-06, K-20, K-55, K-57, K-73, K-94, K-135), written 11 Nov 2026 against `main` at `9c283b6`. Format follows [K3.md](K3.md). The ledger row wins over this spec; this spec names what changes, never restates K1..K3.

**Scope:** sub-veidi (L3) become a living level of the taxonomy: admins create, rename, approve and merge them; people suggest them with "+ Cits"; the wizard, group settings and admin categorisation pick them; the board's Veidi chips open their sub-veidi (K-73 option B). Every Veids (L2) and sub-veids (L3) gets one Unsplash photo with a stored credit, shown on the board's hub card and the hub's head only. The first sub-veidi list and every photo are drafted by us and applied only after the owner approves them on a numbered review page in Būvplāns.

**Not in L3:** images on group cards (they keep the pattern), on L1 or on city hubs; an admin image picker for categories (photos change through the content file, section 7); a fourth level; a Kur change; chat rooms (K4/K5).

**Owner decisions, 11 Nov (all defaults accepted):** D1 images only on hub cards and hub heads; D2 sub-veidi are made like Veidi (admins create, users suggest via "+ Cits", admins approve); D3 picking a sub-veids also tags its Veids; D4 first list 2-4 per Veids where natural, drafted by us, owner strikes/renames on a review page; D5 board chips grouped by Veids in this release; D6 no images for L1; **D7** (owner answer 1) per group up to 2 Veidi and up to 1 sub-veids, both limits constants in `lib/constants`; **D8** (owner answer 2) the category photo is only flair: a thin sliver strip on top of the board hub card (one hub one sliver; two hubs split, each half its own sliver); **D9** (owner answer, 11 Nov): the 3+ hubs list card gives each row a small rounded thumbnail cropped from that category's photo, as its icon; **D10** (Changed, owner 11 Nov): the hub head photo is no strip above the tile; it fills the head tile behind its content, blended with the Tēma tone (grayscale photo under an 82 % tone wash), so the head keeps the height of a no-photo head; on every hub page that has a photo. **D11** (owner, 11 Nov, after approving all 108 photos and the 60 sub-veidi names): cards use the photo as a design element with no credit (board hub card sliver per hub, split halves, 3+ list thumbnails; the hub head sliver on every hub page also without credit); the credit is one quiet line at the bottom of the hub's Pārskats, "Foto: <name> / Unsplash", linked like the banner credits (`lib/banner.ts`, `BannerCredit`). Group cards keep the pattern (D1). D11 overrides the credit chip on the head (L3-20, Invariants). Display rules L3-19..L3-21 follow D8-D11.

**Facts the spec builds on.** `Category` is one self-relation table with `level` 1..3 (`prisma/schema.prisma:105`). L3 read paths exist: `discovery-query` (tags match L1/L2/L3), `hub-path`, `hub-query` (`hubGroupWhere` includes sub-veidi), `hub-note-query` (K-118), `hub-summary` (accepts level 2 or 3), `getTaxonomy` (`L2Category.tags: L3Tag[]`). Writes are L2-only: `TaxonomyService.createPendingL2` (l.322), `createActiveL2` (l.380), `approveL2` (l.420), `mergeL2` (l.507) each check `level !== 1` / `!== 2`. `Group.categoryId` is the L1; L2/L3 live in `Group.tags` (`GroupTags`). The tag picker already renders L3 behind `allowL3` (`TagBrowseList.tsx:38`), but all three callers pass `allowL3={false}`. Seed: 15 L1, 28 L2 (`prisma/seed.ts:148`) + 20 demo L2 (`prisma/demo-data/taxonomy.ts`), 0 L3. `Category` has no image. Curated photos live per L1 in `lib/constants/unsplash-curated.ts` (generated by `scripts/unsplash-curated.mjs`); credit helpers in `lib/banner.ts`, credit chip `components/forms/banner/BannerCredit`.

## Invariants (all sessions; the reviewer checks each)

- Every screen outside the ones listed under Visual baseline renders pixel-identical. Group cards never show a category image.
- **At most three levels.** No service path creates a child of an L3; a sub-veids's parent is always an `ACTIVE` L2 under the same L1.
- **A group with a sub-veids always carries its Veids** (D3), enforced in the service on every write path (create, settings, admin categorisation, merge), not only in the picker.
- **Credit follows the image** (R26 invariant 4): the three image columns are written together; a photo is never shown on a hub head without its credit chip; cards never show a credit (design.md, Banner picker).
- **Taxonomy Law with images** (R26 invariant 1): no image URL in the layout `<style>` block; images are `next/image` elements; `--accent` stays server-set.
- **Nothing applies before the owner approves**: no sub-veids or photo reaches seed, demo or production until the review page's sections are Apstiprināts (L3-3 stop).
- **Expand only**: the schema migration adds nullable columns; the content migration only inserts rows and fills nulls. Nothing renamed or dropped.
- No Prisma outside `lib/services/`; every mutation returns `ActionResponse<T>`, has a submission guard and a shared Zod schema; `lv.json` and `en.json` change together; no new docs besides this spec, the review drawing and the handoff line.

## Motivation and design alignment

Hubs exist per Veids and sub-veids (K-05, K-06, K-57), but with no way to make an L3 the third level is empty and K-20 / K-94 ("sub-hubs at the bottom") show nothing. Reusing the L2 write path for L3 (one parameterised path, not a copy) keeps the Service Law's single owner of taxonomy writes; the hub reads already handle L3, so the release is mostly writes, pickers and content. A photo per Veids gives the hub card and head a face without touching group cards, which keep the Tēma pattern that tells topics apart at a glance (D1). Photos come from Unsplash with stored credit like R26 banners, so the attribution rule and helpers are reused.

### 2.1 Migration `category_image` — L3-01

| Column | Type | Meaning |
|---|---|---|
| `imagePath` | `String?` | the `photo-…` part of an `images.unsplash.com` URL (as `CuratedPhoto.path`); the URL is built with `unsplashImageUrl(path, BANNER_IMG_PARAMS)` |

## 3. Service (L3-1)

### 3.1 `lib/services/taxonomy-write.ts` (new, ≤ 300) — L3-03

`taxonomy.service.ts` is 1051 lines; do not grow it. Move `createPendingL2`, `createActiveL2`, `approveL2`, `mergeL2` (with `createUniqueCategorySlug`, `takenByCity`, `collectMergeNotices` if only they use them) into the new file as `createPending`, `createActive`, `approve`, `merge`, exported through `TaxonomyService` under the new names; update the one caller file (`actions/taxonomy-actions.ts`) and delete the L2 names. Behaviour:

- **Level from the parent:** `parent.level === 1` → child level 2; `parent.level === 2` → child level 3, and the parent must be `ACTIVE`; any other → `TAG_LEVEL_INVALID`. The advisory lock key becomes `pending-topic:<parentId>:<name>` (same shape, works for both levels).
- **Approve/merge** check `level in (2,3)` instead of `=== 2`; merge keeps `pending.parentId === canonical.parentId` (so an L3 merges only into a sibling) and also moves `children` (an L2 merged away hands its L3 to the canonical; slug clashes among them: merge the clashing child into the canonical's child of the same slug, recursion depth 1).
- **Merge moves** `groupsWithTags`, `hubNotes`, `hubCities` (K3-14 clash rule: keep the `OPEN` one), `aliases`, as today, and re-runs the D3 rule on every affected group (L3-04).
- **Slugs:** `createUniqueCategorySlug` already guarantees global uniqueness and the city guard (K3 risk 1); an L3 slug that equals a city segment is refused (`TAG_ALREADY_EXISTS`).
- `bulkApprovePending`, `bulkDelete`, `bulkMerge` (l.901-1051) accept L3 ids too (they filter on `PENDING_REVIEW`; check for hidden `level: 2` filters and widen them).
- `getPendingCategories` (l.756) returns L3 suggestions with their parent path (`Spēles › Galda spēles`); add `parentTitle` to `PendingCategoryWithContext` if missing.
- `getAllL2Categories` → keep the name if only the merge picker uses it, but return L2 and L3 with `level` and `parentId` so the merge view can filter siblings.

### 3.2 Veids auto-tag and limits — L3-04

One pure helper in `lib/services/taxonomy-write.ts`: `withParentTopics(tagIds): Promise<string[]>` adds, for every L3 id, its parent L2 id (deduped, order: each parent before its children). Every write of `Group.tags` calls it before `validateGroupTags`: group create, group settings, `adminUpdateGroupTags`, and the merge re-run (grep `validateGroupTags(` and `tags: { set` in `lib/services`).

`validateGroupTags` (l.640) changes: count L2 ids against `MAX_GROUP_TAGS`, L3 ids against `MAX_GROUP_SUBTAGS` (`TAG_SUB_LIMIT`); the legacy "may keep what it had" rule applies per level; every L3's parent must be in the set (after `withParentTopics` it always is; the check guards direct callers). Removing a Veids from a group removes its sub-veidi (picker does it; the service drops orphan L3 ids instead of failing).

### 3.3 Image reads — L3-05

`getTaxonomy` and the hub context gain `image: { url: string; credit: BannerCredit } | null` built with `unsplashImageUrl` + `toBannerCredit`. An L3 without its own image falls back to its L2's (one join, `parent.imagePath`). Done in L3-1 so L3-3 only renders.

## 15. Risks

1. **Hidden `level: 2` filters.** Bulk actions, `searchL2`, `getPendingTagOptions` and the admin tree may filter on level 2; a missed one silently hides L3 suggestions. Grep `level: 2` and `level !== 2` in `lib/services` and `app/[locale]/admin/categories`.
2. **Limit semantics change.** `MAX_GROUP_TAGS` used to count every tag; legacy groups are fine (no L3 exists), but any client check (`SelectedTags`, `TagPicker` `maxTags`) still counting all tags would block a valid pick.
3. **OR matching on the board.** If a sub-veids is added to `tags` beside its Veids, the filter does not narrow. L3-14 replaces; the reviewer checks the URL.
4. **Unsplash rate limit.** ~140 searches at 50/h: three runs; the cache and resume make it safe. Without `UNSPLASH_ACCESS_KEY` L3-3a stops and reports.
5. **Seed order drift.** Tagging seed groups with sub-veidi can reorder K1 hub rows (activity times). Tag groups that are not in the first rows, or pin dates (`tests/visual/pin-dates.sql`).
6. **Content migration vs admin edits.** A later generated migration must not overwrite an admin rename or a removed photo: keep `DO NOTHING` / `IS NULL`; a deliberate swap sets the new photo only `WHERE "imagePath" = <old path>`.
