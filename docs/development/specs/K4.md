# K4 spec · Matrix trial (spike)

Just-in-time spec for stage K4 of Kanāli ([ledger](kanali.md#feature-ledger), K-71), written 11 Nov 2026 against `main` at `0389ce0`. No drawing: nothing user-facing is built. Ledger rows that this trial must prove: K-08 (room with two Space parents), K-30 (self-hosted Matrix, our own panel), K-38 / K-38c (the site sets power levels; site admins are hub admins), K-38b (signed-out reading of public rooms), K-82 (no private Matrix rooms). K3.md §9 "What K5 needs" lists the hooks K5 will add; K4 only tests that they can work and adds none of them.

**Scope (owner, 11 Nov):** (a) Synapse in `docker-compose.yml` and `docker-compose.server.yml`, its own Postgres database, federation off, registration closed. (b) The site as a Matrix **application service**: one Matrix user per site user `@u_<userId>`, no second password; the site creates Spaces and rooms and sets power levels. (c) Prove five things (F1..F5 below) plus server RAM (F6). (d) One admin-only test page, not linked anywhere, plus a findings section in this file filled by the builder and ledger rows in `kanali.md`. Local first; once the local checks pass, deploy to the home server.

**Not in K4:** the Čats design and pages (K-80, K-81, K-88, K5), group chats (K-36), sign-in from Element/FluffyChat, moderation (K-42), any Prisma migration, any user-visible link, `HubCity.roomId` / `City.spaceId` (K5, K3.md §9).

**Data: no migration.** Rooms and Spaces are found by **Matrix room aliases** in the appservice's exclusive alias namespace (section 3.2), so the site stores nothing. K5 decides whether to cache room ids in columns.

**Size and split: two builder sessions**, each reviewed on its own, run in order.

## Invariants (all sessions; the reviewer checks each)

- **Nothing user-facing changes.** No link to `/admin/matrix` anywhere (not in `AdminPagesNav`, not in the admin dashboard); every visual baseline shows **no diff**; smoke and visual CI run without Synapse.
- **The site runs the same with Matrix down or unset.** Every `MATRIX_*` variable is optional; unset means the test page says "not configured" and no other page calls Matrix. A Synapse outage or night sleep never fails a site deploy or `/api/health`.
- **Service Law:** every HTTP call to Synapse lives in `lib/services/` (`matrix-*.ts`); actions call services; the browser talks to Synapse only through matrix-js-sdk with a token the site issued. No Prisma change.
- **No second password.** Matrix users exist only through the appservice (`/register` with `m.login.application_service`); `password_config.enabled: false`, `enable_registration: false`. Nobody can sign in to Synapse except through the site.
- **Federation off** (`federation_domain_whitelist: []`, no `federation` listener resource, no `.well-known`), and only `/_matrix/client/` is reachable from outside: never `/_synapse/admin`, never `/_matrix/federation`, never `/_matrix/key`.
- **No private rooms (K-82):** only the appservice sender may create rooms or invite; enforced in Synapse by the rules module, not only by our client.
- **Secrets never committed:** `as_token`, `hs_token`, `macaroon_secret_key`, `form_secret`, DB password and the signing key live in git-ignored rendered config (`.matrix/` locally, `/root/ejam-kopa/matrix/` on the server) and `.env`.
- Every action returns `ActionResponse<T>`, starts with `requireSiteAdmin()`, has a submission guard on the client; no hard-coded strings (admin page strings in `messages/*.json` under `admin.matrixTrial`); `lv.json` and `en.json` change together; no new docs besides this spec.

## Motivation and design alignment

K5 builds Čats on Matrix (K-30). Before designing pages around it we need to know that the four structural promises hold on a real Synapse at our scale: one account per site user without a second password, rooms that sit in two Spaces (K-08), signed-out reading (K-38b) and no private rooms (K-82). Each is a server behaviour that could force a different design, so K4 proves them with the cheapest possible surface: one admin page. The application service model keeps the site the single source of identity and power (K-38: the site assigns moderators and writes power levels per room, nothing inherited), so Matrix stays a message store behind our own client. The Service Law puts every Synapse call in `lib/services/` beside the other integrations; the Context Law is untouched (no provider, no hub context change); no migration means nothing to contract later if the trial says "no".

### 2.3 Rules module `ejam_rules.py` — K4-02

Registers spam-checker callbacks via `api.register_spam_checker_callbacks(...)` (Synapse modules API; callbacks return `synapse.module_api.NOT_SPAM` or `Codes.FORBIDDEN`, booleans are deprecated):
- `user_may_create_room(user_id, room_config)` → `NOT_SPAM` only for the configured `sender`, else `FORBIDDEN`.
- `user_may_invite(inviter, invitee, room_id)` → same rule on `inviter`.
- `user_may_create_room_alias(user_id, room_alias)` → same rule.
- `user_may_send_3pid_invite` → `FORBIDDEN` always.

Users still **join** public rooms themselves (`join_rule: public`); that is the K-33a behaviour. Guests cannot join (`guest_access: forbidden`), so they cannot write (K-38b: writing needs sign-in).

### 2.5 Server compose and address — K4-13, K4-14

- `docker-compose.server.yml`: the same `synapse` service without a profile, volume `./matrix:/data`, **no published port**, no `mem_limit`, `restart: unless-stopped`. **Changed 12 Nov:** `deploy/server-deploy.sh` renders the config and starts Synapse on every deploy (`matrix_up`: `render.sh matrix`, `create-db.sql`, `up -d --no-deps synapse`, restart only when the rendered files changed), idempotent and non-fatal (`( matrix_up ) || log`), skipped when `MATRIX_AS_TOKEN` is unset. The workflow copies `deploy/matrix/*` to `/root/ejam-kopa/deploy/matrix/`.
- **Address (default):** `https://ejam.lumm.eu/_matrix/client/…`, routed by the stack's own Caddy. In `deploy/Caddyfile.template`, inside `:3000 { }`, before the app `reverse_proxy`: `handle /_matrix/client/* { reverse_proxy synapse:8008 { flush_interval -1 } }`, `handle /_synapse/* { respond 404 }`, `handle /_matrix/* { respond 404 }` (after the client route; federation, key and admin endpoints are refused by Caddy itself) and keep the existing proxy in a `handle { }`. Same origin as the site (no CORS, no new DNS name or certificate, the host proxy needs no change), and only the client API is reachable. When Synapse is stopped those paths answer 502; nothing else changes. `server_name` is `ejam.lumm.eu`, so users are `@u_<id>:ejam.lumm.eu`.
- App env in the `&app` anchor: `MATRIX_HOMESERVER_URL: ${MATRIX_HOMESERVER_URL:-}` (server: `http://synapse:8008`), `MATRIX_PUBLIC_URL: ${MATRIX_PUBLIC_URL:-}` (`https://ejam.lumm.eu`), `MATRIX_SERVER_NAME: ${MATRIX_SERVER_NAME:-}`, `MATRIX_AS_TOKEN: ${MATRIX_AS_TOKEN:-}`. Runtime only, nothing baked into the image (the browser gets the public URL from the action, section 4.2).

## 4. Services and actions (K4-1)

### 4.1 `lib/services/matrix-client.ts` (new, ≤ 90) — K4-04

`matrixConfig(): { homeserverUrl, publicUrl, serverName, asToken } | null` (null when any is unset) and `asFetch<T>(method, path, body?, asUser?)`: `fetch` against `MATRIX_HOMESERVER_URL` with `Authorization: Bearer <as_token>` (header, not `access_token` query: Synapse's legacy query auth is off by default), `?user_id=<mxid>` when masquerading (identity assertion), 10 s timeout via `AbortSignal.timeout`. Network error or 5xx → `ActionError('MATRIX_UNAVAILABLE')`; a Matrix error body `{ errcode }` is returned typed as `MatrixError` so callers can branch on `M_USER_IN_USE`, `M_FORBIDDEN`, `M_NOT_FOUND`; otherwise `ActionError('MATRIX_FAILED')`. No `any`: response types are explicit interfaces, parsed as `unknown` plus small guards. `server-only` import.

### 4.2 `lib/services/matrix.service.ts` (new, ≤ 150) — K4-05..K4-07

| Method | Does |
|---|---|
| `status()` | `GET /_matrix/client/versions` and `GET /_matrix/client/v3/account/whoami` as the AS; returns `{ configured, reachable, serverName, versions }` |
| `ensureUser(userId)` | `POST /_matrix/client/v3/register` `{ type: 'm.login.application_service', username: 'u_<id>', inhibit_login: true }`; `M_USER_IN_USE` = fine; then `PUT /profile/<mxid>/displayname` as the user with the site name (`UserService` read). K4-05 |
| `sessionFor(userId)` | `ensureUser`, then `POST /_matrix/client/v3/login` `{ type: 'm.login.application_service', identifier: { type: 'm.id.user', user: 'u_<id>' }, device_id: 'EJAM_WEB' }`. The spec invalidates earlier tokens of the same device on a new login, so each user has **one** live web token and no table. Returns `{ userId: mxid, accessToken, deviceId, homeserverUrl: publicUrl }`. K4-05 |
| `ensureSpace(alias, name, topic?)` | resolve `GET /directory/room/<alias>`; on `M_NOT_FOUND` `POST /createRoom` as sender with `creation_content: { type: 'm.space' }`, `room_alias_name`, `preset: 'public_chat'`, `initial_state` (history `world_readable`, guest_access `forbidden`), `power_level_content_override` (4.3). Returns the room id. K4-06 |
| `ensureRoom(alias, name, parents: string[])` | same with no `type`; then for each parent space `PUT /rooms/<space>/state/m.space.child/<room>` `{ via: [server], suggested: true }` and in the room `PUT state/m.space.parent/<space>` `{ via: [server], canonical: <first parent> }`. K4-06 |
| `syncPowerLevels(roomId)` | read `m.room.power_levels`, set `users` = sender 100 + every site admin (`AdminService`/site-role read, `ADMIN` and `OWNER`) at 50, drop other 50s, write back. K4-07 |
| `readPublic(roomId, limit = 30)` | `GET /rooms/<id>/messages?dir=b&limit=` as sender; returns `{ body, ts }[]` **without names** (Owner question 1) |
| `probePrivateRoom(userId)` | as the user: `POST /createRoom { preset: 'private_chat', is_direct: true }` and `POST /rooms/<trial room>/invite`; returns the two errcodes (expected `M_FORBIDDEN`) |
| `hierarchy(spaceId)` | `GET /_matrix/client/v1/rooms/<id>/hierarchy`; returns child room ids |

Split into `matrix-trial.service.ts` (≤ 100) the orchestration `setupTrial(locale)`: pick the seed's first `OPEN` `HubCity` (Galda spēles × Jelgava) through `HubCityService`/`hub.service` reads, `ensureSpace` the topic hub and the city, `ensureRoom` with both parents, `syncPowerLevels` on all three, sender joins (it is the creator), return `{ topicSpace, citySpace, room, aliases, titles }`. Also `runChecks()` returning the F1..F5 results for the page (each `{ id, ok, detail }`).

### 4.3 Power levels — K4-07

`power_level_content_override` on every room and Space: `users_default: 0`, `events_default: 0` (any member writes, K-33a), `invite: 100`, `kick: 50`, `ban: 50`, `redact: 50`, `state_default: 100`, `events: { m.room.name: 100, m.room.power_levels: 100, m.space.child: 100, m.space.parent: 100, m.room.history_visibility: 100 }`. Site admins = hub admins (K-38c) at **50**: they redact and kick, they cannot change structure; the site (100) owns structure. Rooms do not inherit from their Space (K-38): `syncPowerLevels` writes each one.

### 4.4 Actions `actions/matrix-trial-actions.ts` (new, ≤ 90) — K4-08

`setupMatrixTrialAction()`, `matrixSessionAction()` (token for the calling admin), `runMatrixChecksAction()`, `readPublicAction(roomId)`. Each: `requireSiteAdmin()`, call the service, `handleActionError`. No `revalidatePath` (nothing cached). Error codes added to the registry in `types/actions.ts`: `MATRIX_UNAVAILABLE`, `MATRIX_FAILED`, with `errors.*` strings (section 6).

## 7. Server (K4-2)

### 7.1 Steps — K4-15

On the box over SSH (see the server notes the orchestrator holds; never `docker system prune --volumes`; family apps stay up):
1. Add the `MATRIX_*` values to `/root/ejam-kopa/.env` (random 64-char tokens and secrets, `openssl rand -hex 32`; `MATRIX_SERVER_NAME=ejam.lumm.eu`, `MATRIX_HOMESERVER_URL=http://synapse:8008`, `MATRIX_PUBLIC_URL=https://ejam.lumm.eu`).

## 14. Risks

1. **`server_name` is forever.** Every user id, room id and alias embeds it; changing it later means a fresh Synapse database. `ejam.lumm.eu` matches the site; if the site ever moves domain, K5 starts Matrix fresh (cheap while there are no real users).
2. **matrix-js-sdk under Next 16.** ESM-only, large, may pull the WASM crypto package into the bundle. Dynamic import on one admin page; fallback is raw `/sync` (section 5.2). Record the chunk size: it decides whether K5 uses the SDK.
3. **Guest access opens registration of throw-away accounts.** Each signed-out visitor in variant A becomes a Synapse guest user row and a sync loop. Dev only; the server keeps `allow_guest_access: false` unless F4 recommends it and the owner agrees.
4. **Shared Postgres.** Synapse load lands on the site's database container. `cp_max: 5`, own role and database; F6 watches Postgres too. If it hurts, K5 moves Synapse to its own container.
5. **Web tokens are full user tokens.** Anyone holding one can call the client API as that user; the rules module limits the damage to "write in public rooms", which the user can do anyway. K5 adds expiry (`refresh_token`) and issuing to every signed-in user.
6. **Night sleep.** Synapse and open browser syncs drop at night; both should recover alone. A sync that resumes with a large gap is a K5 UX question, not a K4 fix.
7. **Peeking is legacy.** Guest live reading relies on `/events` peeking (`peekInRoom`), which Synapse keeps but the spec has been replacing; a failure here is a finding that points to server-side reading.
