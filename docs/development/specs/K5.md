## Invariants (all sessions; the reviewer checks each)

- **The site runs the same with Matrix down or unset.** `MATRIX_AS_TOKEN` unset or Synapse unreachable: the Čats page shows `hub.chat.unavailable`, every other page renders as today, no Matrix call blocks a hub, Ziņas, request or deploy; `HubCityService.request` still opens the hub (room creation is best effort after the commit, logged on failure). Smoke and visual CI run without Synapse.
- **Service Law:** every Synapse HTTP call lives in `lib/services/` (`matrix*.ts`, `chat-*.ts`); the browser talks to Synapse only through matrix-js-sdk with a token the site issued. `grep -rn "_matrix" app components actions` finds only SDK use inside `components/hubs/chat/`.
- **The site stores no Matrix ids or tokens** (K-139): no Prisma column for rooms or Spaces; tokens live in the browser's memory only (the device id in `localStorage`); every token is a refreshable one (30 min, F1b), never `sessionFor` without `refresh_token`.
- **The site always acts as the sender** for createRoom, aliases, Space children and power levels (F7); per-user identity assertion (`asUser`) only for `join`.
- **No private rooms** (K-82): our client has no create-room, invite or DM path; the rules module stays as K4 left it.
- **Signed out:** reads lines with names (K-142) through the server (K-140), refreshed every 30 s (K-146); no composer, no name card, no profile link, online list shows names as plain text (K-149), no card. Ziņas keep K-41.
- **matrix-js-sdk only on Čats pages**, by dynamic import inside a client component; `/lv` and other hub pages' First Load JS unchanged.
- Context Law: the Čats page hydrates `ChatProvider`; client parts read `useChatContext()`, never prop-drilled role or mod flags. Taxonomy Law untouched (the hub layout sets `--accent`).
- Every action returns `ActionResponse<T>` with uppercase codes; every send/save has `isPending`; Zod only in `lib/validations/chat.ts`; `lv.json` and `en.json` change together; type roles, scale spacing, `Input`/`Textarea`, `line`/`frame`, `rounded-pill` (`npm run ui:check`).

## Motivation and design alignment

The ledger settled what Čats is (K-31..K-35, K-80..K-88) and K4 proved Matrix can carry it (K-139..K-141). K5 builds the drawn page on that: the site is the identity and power source (appservice, K-38), Matrix only stores lines. Rooms by alias keep the site schema clean and make the pre-launch Matrix reset free (K-141). Server reading for signed-out visitors keeps guests off and names coming from the site (K-140, K-142). Private talk stays in the Ziņas inbox through the existing `ChatRequestService` (K-82), so Čats adds no second inbox. Mentions reuse the bell, Jaunumi and the email digest (K-145, K-87), so nothing new to learn. All Synapse traffic sits in services (Service Law); the page reads one provider (Context Law).

## 2. Rooms and login (K5-1)

### 2.1 Aliases — K5-01

Extends [K4 §3.2](K4.md#32-names--k4-03); ids, never slugs.

| Thing | Alias | Parents |
|---|---|---|
| Veids Space (L2) | `#ejk_hub_<l2Id>` (Space) | — |
| City Space | `#ejk_city_<cityId>` (Space), created lazily with its first room | — |
| Hub room (L2 or L3, K-31) | `#ejk_room_<categoryId>` | the L2 Space |
| Topic × city room (K-08) | `#ejk_room_<categoryId>_<cityId>` | the L2 Space (canonical) + the city Space |

Room names: lv `title` from the service ("Šahs", "Šahs · Jelgava"). An L3 needs no Space of its own: Katalogs reads the site DB, Spaces exist for the Matrix side (K-08).

### 2.2 `lib/services/chat-room.service.ts` (new, ≤ 150) — K5-01..K5-04

`matrix.service.ts` is 185 lines: new logic goes here, `MatrixService` keeps the HTTP primitives (move nothing else).

- `aliasFor(room)` where `room = { categoryId, l2Id, cityId? }` → the alias above.
- `ensure(room, locale)`: `resolveAlias` first; else create Space(s) and the room (`ensureSpace`, `ensureRoom`), then `syncPowerLevels`. Two first visitors at once: `M_ROOM_IN_USE` on create → resolve again (never throw).
- `roomIdFor(room)`: resolve only, `null` if missing (readers never create; the page calls `ensure`).
- `close(room)`: delete the alias (`DELETE /directory/room/{alias}`), empty `m.space.child` in both Spaces, `m.room.join_rules` → `invite`. A reopen creates a fresh room under the same alias (K-144: "room gone").
- `syncAllPowerLevels()`: every `#ejk_room_*` of OPEN topic × city hubs and ACTIVE L2/L3 categories whose alias resolves; site admins 50, nobody else (K-38c, F3: the sender is never listed).
- Errors: `MatrixRequestError` from `matrix-client.ts`; callers in pages catch and show `unavailable`.

### 2.3 Hooks — K5-03, K5-04

- `HubCityService.request` at `REQUESTED → OPEN` (K-126): after the transaction, `ChatRoomService.ensure(...)` best effort (`.catch(log)`), so a down Synapse never fails the request. `close` calls `ChatRoomService.close` the same way.
- Site role grant/revoke actions (`site-role.service` callers): after the service call, `ChatRoomService.syncAllPowerLevels()` best effort.
- Backfill: `scripts/matrix-backfill.ts`, `npm run matrix:backfill`: `ensure` for every OPEN topic × city hub and every ACTIVE L2 and L3 hub room, then `syncAllPowerLevels`. Idempotent; the server runs it once after the K5-1 deploy (handoff line). Hub rooms are also ensured lazily by the Čats page (2.5), so the script is a warm-up, not a dependency.

### 2.4 Browser session — K5-05

- Action `chatSession(input)` in `actions/chat-actions.ts` (new, ≤ 120): signed in only (`UNAUTHORIZED`), `chatSessionSchema = { deviceId: /^EJKW_[A-Z0-9]{10}$/ }`; calls `MatrixService.expiringSessionFor(userId, deviceId)` and returns `{ userId, accessToken, refreshToken, expiresInMs, homeserverUrl, deviceId }`. `homeserverUrl` is `MATRIX_PUBLIC_URL`.
- The client makes the device id once (`localStorage['ejk.chat.device']`), keeps tokens in memory, refreshes itself, with no site round trip (F1b). **matrix-js-sdk v45 has no `tokenRefreshFunction`** (K5-1 finding, 12 Nov): its automatic refresh is for OAuth2-native sessions only, so a legacy Synapse refresh token is not used by the SDK; an expired token gives `M_UNKNOWN_TOKEN` with `soft_logout: true` and the sync loop stops. The client therefore calls `client.refreshToken(rt)` then `client.setAccessToken(new)` (and keeps the new refresh token) on a timer 2 min before expiry, and once more on a `soft_logout` error (the SDK's sync loop stops on `M_UNKNOWN_TOKEN`, so after that refresh the client calls `startClient()` again). Reload = a new login with the same device id; the earlier token dies within 30 min (F1). Sign-out from the site: the client calls SDK `logout()` best effort first.
- The SDK refresh path is untested (F1b): the builder proves one refresh by setting `refreshable_access_token_lifetime: 2m` locally for one run and records it in the handoff line.

### 2.5 Join and read — K5-06, K5-07

- Action `openRoom({ hubKey })` (signed in): resolves the hub context, `ensure`, `MatrixService.joinAs(userId, roomId)`, returns `{ roomId }`. Join rate limit (K4 load row): retry once after `retry_after_ms`.
- `ChatRoomService.readPublic(room, 50)` wraps `MatrixService.readPublic` (names from the site, no Synapse row per visitor, K-140); returns `[]` when the room does not exist yet (no create for signed-out reads of an unopened room: the page calls `ensure` only when Matrix is up; a create from a signed-out render is fine, the site is the sender).
- Lines are `m.room.message` with `msgtype: m.text` only; membership events are not shown (no "* Anna ienāca": joins happen on every first open and would be noise).

### 5.4 Mentions and unread dots — K5-24..K5-26

- Composer: typing `@` suggests names from the room's online list and the names already in the loaded log (max 6, `Input`-style list, keyboard ↑↓ Enter); picking one writes `@Name` and adds the mxid to the message's `m.mentions.user_ids`.
- After a successful send with mentions, the client calls `notifyMentions({ hubKey, eventId })`. The service fetches the event as the sender (`GET /rooms/{id}/event/{eventId}`), checks `sender` is the caller's mxid and the event is under 2 min old, takes up to 5 `@u_<id>` from `m.mentions.user_ids`, skips self, users with `chatMentionNotify = false` and users who already have an unread `CHAT_MENTION` with the same link, and creates `CHAT_MENTION` (USER audience) with the room's Čats href. `CHAT_MENTION` joins `EMAIL_DIGEST_TYPES` (digest if `emailNotifications`, K-145). Bell and Jaunumi row like `HUB_NOTE_REPLY`.
- Unread dots (K-145): a `size-2 rounded-pill bg-primary` dot on open tabs and switcher rows whose last message event is after your read receipt (SDK `room.hasUserReadEvent`); the client sends a read receipt for the last visible event when the room is shown and the tab is visible. No numbers, no sound.

### 5.5 `?room=` redirect — K5-27

On any topic hub page (K-57): `?room=<slug>` → an OPEN topic × city hub with that city segment → its Čats page; an ACTIVE L3 slug → that hub's Čats page; else the hub's own Čats page. Done in `[...hub]/page.tsx` beside the `?city=` redirect.

### 5.6 Čats block on Pārskats — K5-28 (K-150, owner 12 Nov)

## Risks

1. **Presence channel exposure.** Every signed-in socket receives the ids (not names) of everyone online; acceptable for cuids, and the channel cap must be raised or presence silently stops at 100. Fallback if Soketi presence misbehaves: online list hidden, count from the room's recent senders.
2. **Catalog cost.** One Synapse call per room for activity; with 60+ rooms per L2 the 60 s cache and the 8-call limit matter. If slow, show activity only for rooms already created and joined.
3. **Token pile-up on reloads** (F1) is bounded to 30 min per token but not zero; a busy reader reloading often holds several live tokens. Acceptable; revisit if Synapse device tables grow (RAM row K-141).
4. **SDK refresh path untested** (F1b): a failing refresh logs the user out of chat after 30 min; the client then calls `chatSession` again silently once before showing `unavailable`.
5. **Lazy creation races:** two first visitors at once; handled by `M_ROOM_IN_USE` → resolve. The rules module must still let the sender create (it does, F7).
6. **Matrix database reset before launch** (K-141): nothing in the site depends on room ids surviving; the backfill script rebuilds everything.
7. **Mention spoofing:** a client could call `notifyMentions` with any event; the service only trusts events whose sender is the caller and that are under 2 min old.
