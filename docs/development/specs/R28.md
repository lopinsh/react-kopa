# R28 spec · Section pictures

Spec for R28, written 27 Oct 2026 against `main` at `ddc64e5` (R27 live). Source: the owner-approved plan of 27 Oct (`r28-plan.md`, applied as written, no added scope). Illustration: [`R27-mockup.html`](R27-mockup.html), its photo row (`photoRow`, `tileBtn`, lines 262-271, CSS `.prow` / `.ph .more` lines 118, 149-152) and its gallery (`dialog#lb`, CSS lines 175-181, script lines 356-372). It is intent, not a pixel spec: the mockup's fixed 168 px tiles, raw `#fff` / `rgb(0 0 0 / .55)` and the "Pievienot attēlus" in the section head are **not** copied (see section 4). Build fluid from 360 to 1920 (AGENTS.md "UI & styling", design.md "Fluid between the drawings").

Rules touched: [AR-50](../redesign.html#AR-50) (Informācija), [AR-47](../redesign.html#AR-47) / [AR-48](../redesign.html#AR-48) (group page desktop / phones), [AR-67](../redesign.html#AR-67) (one pop-up shell), build-plan C5 (group picture) and R26 (banner picker, credit, raw URLs for site admins only). No new AR id, no ledger edit; the handbook carries the new rules (section 8).

**What changes, in one paragraph.** A group's team can add up to 8 pictures to each Informācija section, picked one at a time from the existing banner picker (curated photos of the category, Unsplash search). Visitors see a light photo row under the section text (3 tiles in the first section, 2 in later ones, the last tile "+N" when there are more) that opens a gallery: one dialog with ←/→, a counter and the photo credit. The head picture opens the same gallery with one item. The team removes a picture with × and reorders in the settings section editor. No captions, no uploads.

**Owner defaults (approved, not questions):** max 8 per section; reorder yes (←/→ in the settings section editor; add and remove inline on Informācija); one pick per picker open, saved at once; head picture uses the gallery (single item: no arrows, no counter); seed pictures only on the visual-test group; no captions (alt = section title + number); no file uploads.

**Size and split.** About 20 files, too many for one build of about 80 tool calls. Two builds, each reviewed and pushed on its own; R28-2 starts after R28-1 is pushed. All i18n keys and error codes land in R28-1, so R28-2 does not touch `messages/*.json` or `types/actions.ts`.

## Invariants (the reviewer checks each)

1. **Members-only stays members-only.** A picture leaves the server only inside a `SectionView` that passed the existing filter (`group.service.ts:270`, `visibility !== 'MEMBERS_ONLY' || isMember || isSiteAdmin`). Pictures are mapped inside that `.map`, never fetched or attached separately. Visitor and pending HTML / RSC payload contain no URL of a members-only section's picture.
2. **Service Law.** All Prisma access in `lib/services/section-picture.service.ts` (and the read additions in `group.service.ts`). Actions only do auth, validation, `revalidatePath`. Every action returns `ActionResponse<T>`; failures are `ActionError` codes.
3. **Permission in the service, every call.** `add`, `remove`, `reorder` each call `GroupService.getManagerAccess(groupId, userId)` (`group.service.ts:775`) for the group that **owns the section** (looked up from the DB, never trusted from the client) and throw `FORBIDDEN` when not allowed. A section id from another group gives `SECTION_NOT_FOUND`.
4. **Cap holds under concurrency.** The count and the insert run in one interactive `prisma.$transaction` that first locks the section row (`SELECT id FROM "GroupSection" WHERE id = $1 AND "groupId" = $2 FOR UPDATE` via `tx.$queryRaw`). Two parallel adds at 7 give exactly one success and one `SECTION_PICTURE_LIMIT`. Counting outside the lock is a bug even inside a transaction (Postgres READ COMMITTED).
5. **URL rule (R26 invariant 3 extended).** A picture URL is saved only if `isUnsplashImageUrl(url)` (`lib/banner.ts:28`) or the actor is a site admin; anyone else gets `BANNER_URL_NOT_ALLOWED`. Credit columns are filled only for an Unsplash URL, else both `null` (as `bannerCreditColumns`, `lib/banner.ts:56`).
6. **Expand-only migration.** One new table, no change to an existing column; the running app ignores it (AGENTS.md "Migrations must work with the version still running").
7. **Context Law.** UI pieces read the team flag and group id from `useGroupContext()` (`g.user.isAdmin`, `g.id`); `isAdmin`/`userRole` is never a prop. Pictures arrive as section data (`SectionView.pictures`).
8. **Defensive Coding Law.** Add, remove and every reorder click have a pending guard (`useTransition` `isPending`, control disabled). Validation via the new shared schemas only.
9. **Unchanged:** `InfoSections` behaviour (tabs, scroll-spy, `#part-`, `?part=`, `afterFirst`), section text editing and `reorderSections` / `deleteSection`, the banner picker in its three forms (kinds `group` / `event` look and act as today), `HeadPicture`'s phone strip, Unsplash per-user limits.
10. **Site admin edits are logged** as upsertSection does today (`group.service.ts:896`): when `access.bySiteAdminOnly`, `ModerationService.logAction(userId, 'GROUP_EDIT', 'GROUP', groupId)` after each successful add / remove / reorder.

## 0. Motivation and design alignment

- **The group's own content comes first** (design.md "Page layouts", rule under the table). Pictures sit with the text they illustrate, inside the section, not in a separate gallery page; a section without pictures looks exactly as today.
- **Reuse over new.** `BannerPickerDialog` (one new kind), `PhotoTile`, `BannerCredit`, `trackUnsplashPick`, `assertBannerAllowed` / `bannerCreditColumns`, `Modal` (Overlay: Esc, scrim, focus trap and return), `ConfirmPopover`, the move-button pattern of `SectionRowActions`. One new dialog type (`Gallery`) serves both the section pictures and the head picture, so `HeadPicture` loses its own dialog body.
- **Laws.** Service Law and cross-group checks per invariant 2-3; Constants Law for the cap; Zod only in `lib/validations/`; no colour resolved on the client (pictures are content, not branding).

## 3. Data and server (R28-1)

### 3.1 Migration `add_section_pictures` (expand only)

`npm run db:migrate -- --name add_section_pictures`, then `npm run db:generate`.

```prisma
model GroupSectionPicture {
  id         String       @id @default(cuid())
  sectionId  String
  order      Int
  url        String
  creditName String?
  creditUser String?
  createdAt  DateTime     @default(now())
  section    GroupSection @relation(fields: [sectionId], references: [id], onDelete: Cascade)

  @@index([sectionId, order])
}
```

Add `pictures GroupSectionPicture[]` to `GroupSection`. Nothing else changes; no backfill. Deleting a section or a group cascades (group -> section -> picture).

### 3.2 Constant and schemas

- `lib/constants/index.ts`: `export const MAX_SECTION_PICTURES = 8;` next to `MAX_SECTIONS` (line 74).
- New `lib/validations/section-picture.ts`:
  - `sectionPicturePickSchema = z.object({ url: z.string().trim().url().max(2048), credit: bannerCreditSchema })` (`bannerCreditSchema` from `lib/validations/banner.ts:5`, nullable).
  - `sectionPictureIdsSchema = z.array(z.string().cuid()).min(1).max(MAX_SECTION_PICTURES)` plus a refine "no duplicates".
  - `sectionIdSchema = z.union([z.string().cuid(), z.literal('about')])` for `add` (the virtual about id is `'about'`, `group.service.ts:143`).

### 3.3 Shared helper: the real first section

Extract lines 803-815 of `upsertSection` (virtual `'about'` -> the real first section, created from the description when none exists) into a module-level `async function materialiseAboutSection(groupId: string): Promise<string>` in `group.service.ts`, exported on `GroupService` as `ensureFirstSection(groupId)`. `upsertSection` calls it (behaviour identical: returns the first existing section's id or creates order 0 from the description). The helper runs only after the caller's `getManagerAccess` check.

### 3.4 `lib/services/section-picture.service.ts`

`export const SectionPictureService = { add, remove, reorder }`. Each returns its value directly (no `{ success }`, `services:check`).

- `add(groupId, sectionId, pick: { url; credit }, userId): Promise<{ pictureId; sectionId; slug; l1Slug }>`
  1. `access = await GroupService.getManagerAccess(groupId, userId)`; not allowed -> `FORBIDDEN`.
  2. `assertPictureUrlAllowed(pick.url, isSiteAdminRole(await getSiteRole(userId)))` (both from where `group.service.ts` imports them; `getSiteRole` is `./site-role.service`). `assertPictureUrlAllowed` lives in `lib/banner.ts`: `assertBannerAllowed(url, { current: null, isSiteAdmin })` (an empty url is rejected by the schema first).
  3. `sectionId === 'about'` -> `sectionId = await GroupService.ensureFirstSection(groupId)`.
  4. Interactive `$transaction`: lock row (invariant 4; no row -> `SECTION_NOT_FOUND`), `count` pictures -> `>= MAX_SECTION_PICTURES` -> `SECTION_PICTURE_LIMIT`, `aggregate _max order`, create with `order = max + 1` and credit columns from `bannerCreditColumns(url, credit)` renamed to `creditName` / `creditUser`.
  5. Moderation log (invariant 10), return ids + `GroupService.getGroupSlugs(groupId)` (null -> `NOT_FOUND`).
- `remove(pictureId, userId)`: find picture with `section.groupId`; none -> `NOT_FOUND`; `getManagerAccess(section.groupId)` -> `FORBIDDEN`; delete; orders may keep gaps (read sorts by `order`). Return slugs.
- `reorder(sectionId, ids, userId)`: find section (`groupId`); none -> `SECTION_NOT_FOUND`; access -> `FORBIDDEN`; in one interactive transaction lock the section row, load the section's picture ids; the given ids must be exactly that set (same length, same members) else `VALIDATION_FAILED`; then `updateMany({ where: { id, sectionId }, data: { order: index } })` per id. Return slugs.

### 3.6 Actions (`actions/section-picture-actions.ts`, new file)

`addSectionPictureAction(groupId, sectionId, pick, locale)`, `removeSectionPictureAction(pictureId, locale)`, `reorderSectionPicturesAction(sectionId, ids, locale)`. Pattern of `upsertSectionAction` (`actions/group-actions.ts:236-262`): `auth()` -> `UNAUTHORIZED`; `validateActionData` with the new schemas; call the service; `revalidatePath` the group page and its `/settings` (both `'page'`); fallback codes `SAVE_FAILED` (add), `DELETE_FAILED` (remove), `MANAGE_FAILED` (reorder). ## 10. Risks

- **Leak through a second read path.** Any new query that loads pictures by group (e.g. a future "all pictures") would bypass the section filter. Today only `getGroupWithContext` and `getEditableSections` (managers only) read them; keep it so.
- **Cap race.** Without the row lock two adds both see 7 (invariant 4). `Serializable` isolation would also work but needs retry handling; the lock is the default.
- **Virtual about under concurrency.** Two first adds on a group with no sections could both create an order-0 section (as two first `upsertSection` saves already could). Accept for the prototype; note it in the handoff if seen.
- **Broken images in the visual run.** `images.unsplash.com` is aborted by the stub today (section 7); without the fix the tiles render as broken images with alt text.
- **`SectionEditForm` size.** It is at 134 lines; all reorder logic stays in `SectionPicturesOrder.tsx`.
- **Team view differs from the visitor's** (every tile, no "+N"). The owner checks the public look by signing out; the handbook says so.
