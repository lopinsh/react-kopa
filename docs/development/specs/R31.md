# R31 Dzīvīgums

Owner request 29 Oct (both phases approved): "show me whether the site is alive". It lives at the top of Admin > Moderācija > Aktivitāte (R30, `app/[locale]/admin/activity/page.tsx`), above the existing feed. Rules: AR-68 (admin frame, `scripts/redesign/gen.mjs:165`), design.md "Admin pages are cards (R11b)" (`docs/handbook/design.md:23`), Colour (`design.md:73`). Two sessions:

| Session | Scope | Migration |
|---|---|---|
| **R31-1** | Growth tiles + 12-week bars, participation, group health, demo switch. Derived from existing rows. | none |
| **R31-2** | `User.lastSeenAt`, written at most once a day per user; active users 1/7/30 d, return rate. | `add_user_last_seen_at` (additive) |

R31-2 starts only after R31-1 is reviewed. Each fits one build.

## Goal

At a glance the owner sees: is the site growing (new users, groups, joins, events, sign-ups, and the trend over 12 weeks), are people actually taking part (in a group, talking, posting), which groups are alive and which have gone quiet, and (from R31-2) how many people come back. Demo content is left out unless asked for, so the numbers are the real site.

## Invariants

- Service Law: every read in `lib/services/vitality*.ts`; the page never touches Prisma. Raw SQL only through `prisma.$queryRaw` with `Prisma.sql` fragments (parameters bound, never string-built), as in `lib/services/discovery-text.ts:20`.
- Read only in R31-1. R31-2's single write is `lastSeenAt`, at most once per user per 24 h (see "Last seen write").
- Admin only: the page keeps `requireAdminPage(locale, '/admin/activity')`. Every site admin sees the panel (not owner only).
- One demo definition for every number (see "Demo"). The feed (R30) is not filtered.
- Counts only. No names of who wrote a message, no message or post text anywhere in the panel.
- Colour: neutrals plus the site colour `--primary` only. No colour per series, no green/red for up/down (colour means category or status, `design.md:73`). No chart library (none is installed; inline SVG).
- Numbers through next-intl `format.number` (percent with `style: 'percent'`), dates through `createDateFormatter` / `useDateFormatter` (`lib/date-format.ts`), never `toLocale*`.
- None of the 12 visual baselines changes (no screen in `tests/visual/` is touched; the privacy page change in R31-2 is not in the set).

## Definitions (R31-1)

All windows are rolling from one `now` taken once per request in the service: 7 d = `[now-7d, now)`, 30 d = `[now-30d, now)`, previous 30 d = `[now-60d, now-30d)`. "Total" = rows that exist today (deleted users/groups cascade away; see Risks).

| Series key | Rows | Time | Demo row when |
|---|---|---|---|
| `users` | `User` | `createdAt` | the user is demo |
| `groups` | `Group` (hidden ones included) | `createdAt` | the group is demo |
| `joins` | `Membership`, role `MEMBER` or `ADMIN` | `joinedAt` | user or group is demo |
| `events` | `Event` | `createdAt` | its group is demo |
| `signups` | `Attendance`, status `GOING`, `PENDING`, `WAITLISTED` | `joinedAt` | user or event's group is demo |

Same row choices as R30's `MEMBER_JOINED` and `EVENT_SIGNUP` (`specs/R30.md` "Sources"), so the feed and the tiles agree. OWNER memberships are covered by `groups`; PENDING memberships are not joins.

Participation (real users and real groups only, unless demo shown):
- **In a group**: users with at least one membership of role `OWNER`, `ADMIN` or `MEMBER`; shown as a percent of all users, plus the count of users in none.
- **Members per group**: mean of each group's `OWNER+ADMIN+MEMBER` count over all groups (one decimal); count of groups with at least `VITALITY_MIN_MEMBERS = 3`.
- **Chat messages**: `Message.createdAt` in 7 d and 30 d (direct and group chats together); demo when the sender is demo.
- **Announcements**: `Post.createdAt` in 7 d and 30 d (archived included); demo when author or group is demo.

Group health, over groups that are **not hidden** (`hiddenAt IS NULL`; hidden ones are moderation's business) and not demo:
- **Empty**: no member besides the owner (`ADMIN+MEMBER` count is 0). Checked first: an owner posting alone is still empty.
- **Active**: otherwise, when in the last 30 d there was any of: a membership `joinedAt` (role MEMBER/ADMIN), a `Post.createdAt`, a `Message.createdAt` in a conversation with `originGroupId` = the group, an `Event.createdAt`, or an event of the group with `startDate` in `[now-30d, now+30d]` (a meet-up that happened or is coming counts as life).
- **Quiet**: the rest.
- `lastActivity` = the greatest of those timestamps (all time, not only 30 d; `startDate` only when `<= now`), falling back to `Group.createdAt`.

## Demo (R31-1)

Marker: `DEMO_EMAIL_DOMAIN = 'demo.ejam.invalid'` (`prisma/demo-data/types.ts:66`; `prisma/demo.ts:19` builds `${username}@${DEMO_EMAIL_DOMAIN}`). A demo user has an email ending `@demo.ejam.invalid`; a demo group is one whose OWNER membership is a demo user (`prisma/demo.ts` only creates groups owned by demo users, including the fallback groups at `:334`). There is no better marker.

- Re-export the constant from `lib/constants/vitality.ts` (`export { DEMO_EMAIL_DOMAIN } from '@/prisma/demo-data/types'`), so the domain has one source. `prisma/demo-data/types.ts` stays import-free (the runner image copies only `/prisma`).
- In SQL: `demoUserIds` = `SELECT id FROM "User" WHERE email LIKE ${'%@' + DEMO_EMAIL_DOMAIN}`; `demoGroupIds` = `SELECT "groupId" FROM "Membership" WHERE role = 'OWNER' AND "userId" IN (demoUserIds)`. Exclude with `col NOT IN (…)`. Users with a null email are real; never write `NOT (email LIKE …)` on the user row itself (null makes the row vanish).
- One helper builds the fragments: `demoFilter(includeDemo)` returns `{ user(col), group(col) }`, each `Prisma.sql\`TRUE\`` when demo is shown.
- Switch: `?demo=1` (exactly `'1'`, anything else is off). The page renders a `FilterChip` "Rādīt ar demo" (`components/ui/FilterChip.tsx`, selected when on) as a `Link` to the same page with `demo` toggled and `type` kept. When off, one muted line under the panel title says demo is left out.
- `ActivityFeed.tsx:30` must keep `demo` when it swaps `?type=` (build the query from `useSearchParams`); the feed itself ignores `demo`.

## Queries (R31-1)

Prisma `DateTime` columns are `timestamp(3)` without zone, holding UTC. Weeks are Monday weeks in `DEFAULT_TIME_ZONE` (`lib/time-zone.ts:7`, Europe/Riga), the admin's zone, fixed (not the viewer cookie, so two admins see the same buckets).

- Local time of a column: `(col AT TIME ZONE 'UTC') AT TIME ZONE 'Europe/Riga'`. Of a bound JS date: `${now}::timestamptz AT TIME ZONE 'Europe/Riga'`. Window bounds compare in UTC: `col >= (${since}::timestamptz AT TIME ZONE 'UTC')`. Put these in two small helpers; do not rely on the DB session `TimeZone`.
- **Per series, one query** (5 in all, run in `Promise.all`): a `src` subquery `(at)` for the series' rows with the demo filter, then
  - `count(*)`, `count(*) FILTER (WHERE at >= since7)`, `… since30`, `… since60 AND at < since30` as `int`;
  - and the 12 weeks: `generate_series(weekStart - interval '11 weeks', weekStart, interval '1 week')` left-joined on `date_trunc('week', local(at))`, giving `to_char(wk, 'YYYY-MM-DD')` and `count(src.at)::int`, oldest first. Either two statements or one with a CTE; the service returns 12 points always (zero weeks included).
- **Participation**: one query with scalar subqueries (users, users with a membership, groups, sum of members, groups with ≥ 3, messages 7/30, posts 7/30). Prisma `count` calls are fine instead if the demo filter can be written the same way; one definition beats mixing, so default to SQL.
- **Group health**: one query returning per eligible group `id`, `members` (ADMIN+MEMBER count), `active` (bool per the definition), `lastActivity`. Classify in TS. Then one `prisma.group.findMany({ where: { id: { in: quietIds } } })` selecting `name`, `slug` and the category chain `TaxonomyResolver.resolve` needs (as `activity-sources.ts` does), for links `/${l1Slug}/group/${slug}`.
- Quiet list: sorted by `lastActivity` ascending (longest asleep first), at most `VITALITY_QUIET_LIMIT = 50` rows plus "un vēl N".
- Cast every `count` to `int` (`::int`): Postgres returns `bigint`, which Prisma hands back as `BigInt`.

Typed result (`lib/services/vitality.service.ts`):

```ts
export type VitalitySeriesKey = 'users' | 'groups' | 'joins' | 'events' | 'signups';
export type VitalitySeries = { key: VitalitySeriesKey; total: number; last7: number; last30: number; prev30: number; weeks: { week: string; count: number }[] };
export type QuietGroup = { id: string; name: string; href: string; lastActivity: Date };
export type VitalitySnapshot = {
  includeDemo: boolean;
  series: VitalitySeries[];
  participation: { users: number; inGroup: number; groups: number; avgMembers: number; groupsMin3: number; messages7: number; messages30: number; posts7: number; posts30: number };
  health: { active: number; quiet: number; empty: number; quietGroups: QuietGroup[]; quietMore: number };
  presence: VitalityPresence | null; // R31-2; null in R31-1
};
```

`VitalityService.getSnapshot({ includeDemo }): Promise<VitalitySnapshot>`. SQL and fragments go in `lib/services/vitality-sql.ts`; keep each file under ~200 lines.

## Last seen write (R31-2)

Schema: `User.lastSeenAt DateTime?` with a doc comment ("Day-level last visit (R31): written at most once per 24 h; null = not seen since R31-2 shipped"). No index (prototype size; see Risks). Migration `npm run db:migrate -- --name add_user_last_seen_at`; additive, ships with the code.

Where (default): **the Auth.js `jwt` callback** in `lib/auth.ts:85`, next to the role recheck (`ROLE_RECHECK_MS`, `lib/auth.ts:28`, `:99`). Why: `proxy.ts:27` wraps every page request in `auth()`, which runs the `jwt` callback and re-issues the session cookie, so a timestamp kept in the token gates the write without any DB read; the role recheck already relies on the same path. A layout helper would run in a server component, which cannot rewrite the cookie, so it would need a DB read on every request to know whether to write. Server actions post to page paths, so they pass the proxy too; `/api/*` does not, which is fine.

- Add `LAST_SEEN_EVERY_MS = 24 * 60 * 60_000` in `lib/auth.ts` beside `ROLE_RECHECK_MS`.
- In the callback, after the existing branches: when `token.id` and `Date.now() - Number(token.lastSeenWrittenAt ?? 0) > LAST_SEEN_EVERY_MS`, call `PresenceService.touch(token.id)` and set `token.lastSeenWrittenAt = Date.now()`. On sign-in (`user` set) it runs too, so a sign-in counts as a visit.
- `lib/services/presence.service.ts`: `touch(userId: string): Promise<void>` = `prisma.user.updateMany({ where: { id: userId, OR: [{ lastSeenAt: null }, { lastSeenAt: { lt: dayAgo } }] }, data: { lastSeenAt: new Date() } })`. The DB-side condition makes a repeat harmless (several `auth()` calls in one request before the new cookie lands each find 0 rows). Wrap the call in the callback in `try/catch` with `console.error`: a failed write must never sign anyone out or break a page.
- No change to the `session` callback; `lastSeenWrittenAt` is not exposed to the client.

## Presence tiles (R31-2)

`VitalityService.getSnapshot` fills `presence: VitalityPresence`:

```ts
export type VitalityPresence = { active1: number; active7: number; active30: number; cohort: number; returned: number; since: Date | null };
```

- `activeN`: real users with `lastSeenAt >= now - N days` (N = 1, 7, 30).
- Return rate: `cohort` = users with `createdAt` in `[now-60d, now-30d)`; `returned` = those of them with `lastSeenAt >= now-30d`. Shown as "N no M (X %)"; M = 0 shows "—".
- `since` = `min(lastSeenAt)` over all users (the day tracking started). Plain Prisma (`count`, `aggregate _min`) with the same demo rule is fine here, but keep one style: add these as one more SQL query in `vitality-sql.ts`.
- A fourth card **Apmeklējums** goes first, above Izaugsme: three numbers (24 h, 7 d, 30 d) and the return rate line with a one-line definition. Under it, muted: "Skaitīts kopš {date}." and, while `since > now-30d`, "Atgriešanās rādītājs būs precīzs no {since+30d}." (both from `since`; when `since` is null: "Vēl nav datu.").

Privacy: `messages/*.json` `privacy.data3` names what is stored about activity; append one sentence to it (keys below), so the privacy page tells the truth.

## Risks

- **Totals are survivors.** Deleted users and groups (and their memberships, events, sign-ups) drop out of every count and every past week, so a week can shrink after the fact. Honest enough for "is it alive"; a true history needs a daily snapshot table (later, if wanted).
- **`joinedAt` moves.** `Attendance.joinedAt` resets on status change (`event.service.ts:773`); membership time is the request time for request groups (R30 Risks). A sign-up can move weeks.
- **Cost.** About eight aggregate queries per page view, unindexed on `User.createdAt`, `Membership.joinedAt`, `Event.createdAt`, `lastSeenAt`. Fine at prototype size; if the page gets slow, add indexes (additive) or cache the snapshot for a minute with `unstable_cache` keyed by `includeDemo`.
- **Last seen is personal data.** Day-level only, admin-only, shown as counts; the privacy page says so. Proxy-only refresh means a user who only hits `/api/*` (none today) is not counted.
- **Cookie refresh assumption.** The R31-2 gate relies on `auth()` in `proxy.ts` re-issuing the cookie, as the role recheck already does. If the acceptance check shows repeated writes, the DB condition still caps it at one row update per day; report it rather than adding a per-request read.
