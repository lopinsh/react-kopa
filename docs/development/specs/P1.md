# P1 spec · Three app processes

One build session (P1-1). Infra only: no app code, no visual change, no migration, no i18n keys, no screens in `tests/visual/` change.

## 0. Goal and why
Load test 25 Oct: `/lv` tops at ~12 req/s, CPU 60 % idle, one Node process pegs one core of the 4-core i5-4590 (7.7 GB, shared with Jellyfin). Run **3 app containers per colour** behind the stack's Caddy so the app can use ~3 cores; the fourth stays for Postgres, Soketi, Caddy and Jellyfin. Blue/green semantics stay: a deploy never drops requests, and a failed deploy leaves the old colour serving.

## Invariants (reviewer checks each)
- `db`, `soketi`, `proxy` services, the `db_data` bind mount and host port `:3000` unchanged; Soketi and DB config untouched.
- Migrations still run in `deploy.yml` before the script, against the running old colour (expand → contract).
- Any new-colour container unhealthy → stop all new containers, Caddyfile not touched, exit 1, old colour keeps serving.
- Old colour stops only after the proxy answers `/api/health` through the new upstreams.
- Same image tag for all 3 processes of a colour (one `pull`), so build ID and the build-time Server Actions key are identical across them.

## 1. Containers (`docker-compose.server.yml`)
- Replace `app-blue` / `app-green` with six explicit services built from the existing `&app` anchor: `app-blue-1..3`, `app-green-1..3`, `container_name: ejam-kopa-app-<colour>-<n>`. Explicit services, not `deploy.replicas`: Caddy needs one stable DNS name per upstream.
- Add to the anchor: `mem_limit: 768m` and `NODE_OPTIONS: "--max-old-space-size=512"`. No CPU limit (a Node process uses ~1 core anyway; a cap only hurts bursts). During a swap 6 containers run for ~15 s: worst case ~4.6 GB by limit, real use well under.
- Healthcheck, env, `depends_on`, `restart: unless-stopped` stay as in the anchor.
- Update the comment block above the services (3 per colour, why).

## 2. Proxy (`deploy/Caddyfile.template`)
- `reverse_proxy __UPSTREAMS__ { ... }`; the script fills `__UPSTREAMS__` with `app-<NEW>-1:3000 app-<NEW>-2:3000 app-<NEW>-3:3000`. The old colour is **not** listed: Caddy 2.8 has no primary/backup groups, and listing stopped upstreams in a balancing policy sends first tries to dead names. The old colour's fallback role moves to the script (section 3, rollback).
- Default `lb_policy cookie ejk_lb` with `fallback least_conn` (verify the exact subdirective against the Caddy 2.8 `reverse_proxy` docs before writing; if 2.8 lacks `fallback`, use plain `cookie` whose default fallback is random). Why sticky: `unstable_cache` and `revalidateTag`/`revalidatePath` are per process (section 4); a sticky browser sees its own writes at once. Load-test tools without a cookie jar spread randomly, which is what the test needs. The cookie is a strictly technical one (no consent needed); it holds an upstream hash, nothing about the person.
- Keep `lb_try_duration 15s`, `lb_try_interval 250ms`, `fail_duration 5s`, active `health_uri /api/health` (2 s / 2 s), `flush_interval -1`. A cookie pointing at a down or old upstream falls back and is rewritten.
- Update the header comment (no more primary/standby).

## 3. Script (`deploy/server-deploy.sh`)
- Helpers: `NEW_SVCS="app-$NEW-1 app-$NEW-2 app-$NEW-3"`, `ctr() { echo "ejam-kopa-$1"; }`.
- Active colour: blue if `ejam-kopa-app-blue-1` **or** the legacy `ejam-kopa-app-blue` is running, else green.
- `$COMPOSE pull app-$NEW-1` (one pull, same image), then `$COMPOSE up -d --no-deps --force-recreate $NEW_SVCS`.
- Health wait: one shared 180 s deadline; loop until all 3 report `healthy`; if any is not running or the deadline passes, print `docker logs --tail 40` of each unhealthy one, `$COMPOSE stop $NEW_SVCS`, log "aborted, $OLD keeps serving", exit 1. Log `free -m` once before starting the new colour.
- Render: `sed -e "s/__UPSTREAMS__/app-$NEW-1:3000 app-$NEW-2:3000 app-$NEW-3:3000/"` into `Caddyfile.next`; keep the `caddy validate` step and the `mv`.
- Keep the copy of the previous `caddy/Caddyfile` as `caddy/Caddyfile.prev` before the `mv`. Proxy check fails after 30 s → restore `Caddyfile.prev`, reload, `$COMPOSE stop $NEW_SVCS`, exit 1 (old colour was never stopped, so it serves again). Keep the existing legacy-`ejam-kopa-app` branch as is.
- Stop old after drain: `docker stop -t 30` by container name for `ejam-kopa-app-$OLD-1..3` that run, **and** the legacy single-colour container `ejam-kopa-app-$OLD` if it exists (first P1 deploy only); then `docker rm` that legacy one so compose stops reporting it as an orphan. Use `docker stop` by name, not `$COMPOSE stop`, because the old service names no longer exist in the file.
- Image cleanup: read the repo from `ejam-kopa-app-$NEW-1`. Unchanged otherwise.
- Header comment: say 3 per colour.
- `deploy.yml` names no container (only comments): no change needed. Confirm the step that copies `server-deploy.sh` and `Caddyfile.template` to the server still copies both.

## 4. In-process state (checked, 26 Oct)
- Sessions: Auth.js `strategy: "jwt"` with the shared `AUTH_SECRET` → any process verifies any session. Fine.
- No file writes (`writeFile`/streams) in `lib`, `actions`, `app`; no in-memory rate limits; module-level `new Set` in `lib/auth.ts`, `lib/utils/notification-text.ts`, `lib/feedback/capture.ts` are constants. Prisma client singleton is per process (pool ~9 each; 6 processes during a swap ≈ 54 < Postgres default 100).
- Server Actions encryption key: generated at build, baked into the image, so the 3 processes of a colour share it. Across colours it already differs today (a page loaded on old, action posted to new after the swap); unchanged by P1. `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` is not needed for this release.
- **`unstable_cache` is per process** (`city`, `discovery`, `event`, `message-override`, `taxonomy`, `theme` services). `revalidateTag`/`revalidatePath` clear only the process that ran the action; the other two serve stale data until their `revalidate` window ends: 60 s (cities, message overrides, some events), 300 s (theme, home lists), 3600 s (taxonomy, one discovery query). The sticky cookie hides it from the writer; other visitors may see a new group or renamed category late. See owner question 1.

## Acceptance
1. A deploy from `main` succeeds; `docker ps` shows `ejam-kopa-app-<NEW>-1..3` healthy, old colour stopped, legacy `ejam-kopa-app-<OLD>` removed.
2. A second deploy swaps back cleanly (green ↔ blue), no 502 during either (run `hey -z 60s -c 5 https://ejam.lumm.eu/lv` across the deploy; zero non-2xx).
3. Site works signed out and signed in: board, group page, join, a Ziņas message (Soketi), an admin save.
4. Load test `/lv` at c=10 (same tool and settings as 25 Oct) ≥ 25 req/s; `docker stats` shows all 3 processes busy.
5. Forced failure (temporarily bad env on one new container, or local dry run) → script exits 1, old colour serves, Caddyfile unchanged.
6. `bash -n deploy/server-deploy.sh` and `caddy validate` on the rendered template pass.

## Risks
- RAM pressure from Jellyfin transcodes plus 6 containers mid-swap: limits in section 1; watch `free -m` in the deploy log.
- Cache staleness across processes (section 4).
- First P1 deploy migrates from `app-<colour>` to `app-<colour>-N`: the legacy detection and stop/rm in section 3 cover it; reviewer walks the script once for "old = legacy blue" and once for "old = blue-1..3".
