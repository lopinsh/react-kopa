# K2 spec · Ziņas (hub notes)

Just-in-time spec for stage K2 of Kanāli ([ledger](kanali.md#feature-ledger), K-71), written 11 Nov 2026 against `main` at `240dbe4`. Drawing: [`docs/development/kanali/hub.html`](../kanali/hub.html) v18 (read its source by function, never the whole file; line numbers are v18). The ledger row wins over the drawing; the drawing wins over this spec where they disagree, except where this spec names an owner question. K1 is built ([K1.md](K1.md)): this spec only names what changes in it.

**Scope:** Ziņas, the hub's post-it notes (K-26, K-27, K-77): write, edit, delete, renew; the grouped Ziņas page with Visas / Manas, search and Kur; public replies; the private "Rakstīt ziņu" chat request in the Ziņas inbox; Ziņot into the existing Report queue; notifications; the Ziņas block and tab row on Pārskats; Ziņas in the hub menu. Built from **Confirmed** rows K-26, K-27, K-27a, K-41, K-77, K-79, K-83, K-86, K-87, K-89, K-90, K-95, K-98, K-111, K-09b, K-38c and the owner decisions of 11 Nov, recorded as **K-116..K-122**.

**Not in K2:** city hubs (K3), Čats and its member list (K4/K5; K-82's request from Čats reuses this release's `ChatRequest` later), hub admins other than site admins (K-38c), blog posts (K-24), moderation tools beyond Report (K-42). Ziņas do not feed the Aktivitāte feed or the board hub card.

**Data: one additive migration** (`hub_notes`, expand only): three new tables, one enum, two nullable `Report` columns. Nothing renamed or dropped.

**Size and split: three builder sessions**, each one commit set, each reviewed on its own. K2-2 and K2-3 depend on K2-1; K2-3 may start before K2-2 is merged only if it touches no hub page file (it adds to the note row, so run them in order).

## Invariants (all sessions; the reviewer checks each)

- Every screen outside the hub pages renders pixel-identical (visual baseline; only the screens listed under Visual baseline may change). The Ziņas inbox (`messages` baseline) shows no change while a viewer has no chat requests.
- No Prisma outside `lib/services/`; hub pages still read one `HubContext` via `useHubContext()`; `--accent` stays server-side in the hub layout.
- **Signed out gets no names**: for a viewer without a session the service returns `author: null` on notes and replies (data, not only display). Nothing about a person's groups or chat requests reaches a signed-out page.
- **Expired is gone**: a note with `expiresAt ≤ now` and its replies are read by no public path (hub pages, Pārskats, search, notification links); only its author sees it, in Manas.
- **Decline is silent**: the sender's data and UI for a DECLINED request are byte-for-byte those of a PENDING one; no notification, no timing or count tells them apart.
- Everyone edits and deletes only what they wrote; a note's author cannot touch others' replies; site admins delete anything (K-119, K-38c). Permission checks live in the service, never only in the UI.
- At most `HUB_NOTE_ACTIVE_MAX` active notes per person across the site, enforced in the service under a lock (K-27a).
- Every mutation returns `ActionResponse<T>`, has a submission guard, validates with shared Zod schemas; no hard-coded strings; `lv.json` and `en.json` change together; no new docs besides this spec.

## Motivation and design alignment

Ziņas let someone without a group say "I'm looking for people for this" in the place where those people look (K-26), as plain notes, not a feed or a chat (K-27). The release reuses the hub frame and K1's accordion rows (one row pattern for feed, events and notes, K-79), the site's inbox for private talk (K-82: private chat lives only in the Ziņas inbox), the Report queue and the notification bell + R33 digest (K-87: nothing new). One `HubNoteService` owns notes and replies (Service Law); requests sit beside `MessageService`, which already owns pair chats. Expiry and the 3-note limit keep the wall small and current without a moderation team (K-27a, K-38c).

## 2. Data (K2-1)

### 2.1 Migration `hub_notes` — K2-01

`npm run db:migrate -- --name hub_notes`. All additive; relation names as needed on `User`, `Category`, `City`, `Group`.

```prisma
enum ChatRequestStatus { PENDING ACCEPTED DECLINED }

model HubNote {                 // a Ziņa
  id         String   @id @default(cuid())
  authorId   String
  categoryId String             // the hub: an ACTIVE L2 or L3 Category
  cityId     String?            // K-116: optional, never defaulted from the author
  groupId    String?            // K-117: one of the author's groups in that hub, else "Visai kopienai"
  content    String
  expiresAt  DateTime           // createdAt + HUB_NOTE_DAYS; renew sets now + HUB_NOTE_DAYS
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt
  // author Cascade, category Cascade, city SetNull, group SetNull
  replies      HubNoteReply[]
  chatRequests ChatRequest[]
  reports      Report[]
  @@index([categoryId, expiresAt])
  @@index([authorId, expiresAt])
}

model HubNoteReply {
  id String @id @default(cuid())
  noteId String; authorId String; content String
  createdAt DateTime @default(now()); updatedAt DateTime @updatedAt
  // note Cascade, author Cascade
  reports Report[]
  @@index([noteId, createdAt])
}

model ChatRequest {
  id String @id @default(cuid())
  senderId String; recipientId String
  noteId String?                // SetNull: the request outlives its note
  content String                // the first message, posted into the chat on accept
  status ChatRequestStatus @default(PENDING)
  conversationId String?        // set on accept
  createdAt DateTime @default(now()); decidedAt DateTime?
  // sender Cascade, recipient Cascade, note SetNull, conversation SetNull
  @@unique([noteId, senderId])  // K-120: one request per person per Ziņa (recipient = the note's author)
  @@index([recipientId, status])
  @@index([senderId, status])
}

// Report: add
targetNoteId      String?   // relation HubNote, onDelete Cascade (a report on deleted content has nothing to act on)
targetNoteReplyId String?   // relation HubNoteReply, onDelete Cascade
```

No `deletedAt`: delete is a hard delete (cascades replies and reports). Expired notes stay as rows (the author can renew them); no purge job in K2.

## 3. Service (K2-1)

### 3.1 `lib/services/hub-note.service.ts` (new, ≤ 150) + `hub-note-query.ts` (new, ≤ 110)

- **K2-03** `HubNoteService.list(hub, { cities, q, tab, take }, locale, viewer?) → HubNoteList`. Where (`hubNoteWhere` in the query file): `categoryId = hub.id` or, on an L2 hub, `category.parentId = hub.id` (K-118); `expiresAt > now` (except `tab 'mine'`, which is the viewer's own in this hub incl. expired, newest first, flat); Kur (K-116, K-09b): `OR [{ cityId: null }, { city.slug in cities }]` when cities are set; `q`: `content contains, insensitive`. Returns rows `{ id, content, createdAt, expiresAt, city: { slug, name } | null, group: { name, href } | null, topic: { slug, title, href }, author: { id, name, image, avatarSeed, flair } | null, replyCount, mine, canDelete, request: 'none' | 'pending' | 'open' | 'hidden' }` (request filled by K2-23; K2-1 returns `'none'`). The group is shown only while it is PUBLIC and unhidden; otherwise the row counts as "Visai kopienai". Order: newest first.
- **K2-04** Grouping (K-111, K-118) as a pure helper `groupNotes(rows, hub)` in the query file: sections = the hub's own notes first (heading = the hub title), then one section per sub-veids that has notes (heading = its title, ordered by newest note); inside each section boxes per group (label = group link; signed out: plain text), ungrouped last under "Visai kopienai". On an L3 hub, or when only one section exists, no section heading. Drawing `ZG` / `zinasGrouped()` l.323-339 shows the shape (its top-level "Visai kopienai" section = the hub's own ungrouped notes).
- **K2-05** `create(viewerId, input)`: the category is ACTIVE and is the hub or one of its L3 children; the group (if any) is in `hubGroupWhere` for that category and the viewer is a non-PENDING member (K-117); the city is ACTIVE. Limit: in one transaction take `pg_advisory_xact_lock(hashtext('hub-note:' + viewerId))` (as `getOrCreateDirectChat`, `message.service.ts` l.574), count `expiresAt > now`, `≥ HUB_NOTE_ACTIVE_MAX` → `HUB_NOTE_LIMIT`. Returns `{ id, href }` (href = the note's own hub's Ziņas page with `?z=`).
- **K2-06** `edit(viewerId, id, input)`: author only, active notes only. `delete(viewerId, id)`: author or site admin (`isSiteAdmin`), hard delete. `renew(viewerId, id)`: author only; `expiresAt = now + HUB_NOTE_DAYS`; renewing an **expired** note counts against the limit (same lock) and deletes its replies in the same transaction (K-121: replies vanished with the expiry; a renewed note starts clean). Renewing an active note keeps its replies.
- **K2-07** `activeCount(viewerId)` for Manas ("{n} no 3 visā vietnē") and the compose form; `composeOptions(hub, viewerId, locale)`: Veids list (the hub, plus its sub-veidi on an L2 hub), the viewer's groups per Veids (from `hubGroupWhere`, non-PENDING membership), active cities (reuse the city list the Kur filter already loads in `HubService.getCityCounts` / `city.service.ts`).
- **K2-08** Signed out: when `viewer` is undefined, `author` is `null` and replies carry no author (K-41).
- `HubService.getHubContext` stays as is; `hubPages()` gains the `messages` page (K2-10).

### 3.2 Report targets — K2-09

`ReportService.createReport` takes `targetNoteId?` / `targetNoteReplyId?` (exactly one target set, else `VALIDATION_FAILED`); `getPendingReports` returns the note or reply text, its author name and the hub link; `deleteReportedContent` deletes a reported note or reply (hard delete, resolves the report in the same transaction, as for events). `actions/report-actions.ts` accepts the new targets and notifies admins as it does today (`ADMIN_REPORT`).

### 3.3 Actions `actions/hub-note-actions.ts` (new, ≤ 120)

`createHubNote`, `editHubNote`, `deleteHubNote`, `renewHubNote` (K2-1); `replyToHubNote`, `editHubNoteReply`, `deleteHubNoteReply`, `sendChatRequest`, `answerChatRequest` (K2-3; requests may live in `actions/message-actions.ts` instead). Each: `auth()` → `UNAUTHORIZED`; schema parse; service; `revalidatePath` of the note's hub pages (`[locale]/[l1Slug]/[...hub]`, layout) and, for requests, `/messages`; `handleActionError`.

## 6. Replies, chat request, report UI (K2-3)

### 6.1 Replies — K2-21, K2-22

- `HubNoteService.reply(viewerId, noteId, content)` (active note only, else `NOT_FOUND`), `editReply` (author only), `deleteReply` (author or site admin; **the note's author cannot**, K-119). Replies are read only with their note (`list` with `?z=` or when a row opens: default, load replies with the page for rows already open by `?z=`, others through a small server action `getHubNoteReplies(noteId)` on first open, so a page of 200 notes does not read every reply).
- Open row: replies oldest first as the drawing's left-ruled block (l.320): **name** · text (signed out: text only), "pirms N" meta; own reply: Labot / Dzēst; admin: Dzēst; others: Ziņot. Below: `Textarea` + "Atbildēt" (signed in), "Ienākt, lai atbildētu" (signed out).

### 6.2 "Rakstīt ziņu" chat request (K-83, K-82, K-120) — K2-23..K2-26

- **K2-23** Button state on others' notes (service fills `request`): an existing DIRECT chat with the author (any state) → `'open'`: the button opens it (`/messages?c=`), no request; `allowDirectMessages = false` → `'hidden'`; a request from the viewer on this note exists (PENDING **or DECLINED**) → `'pending'`: a disabled quiet button "Gaida apstiprinājumu"; else `'none'`: the button opens a small form (`Textarea`, "Sūtīt") in the row.
- **K2-24** `lib/services/chat-request.service.ts` (new, ≤ 130): `send(senderId, noteId, content)` (note active, sender ≠ author, author allows DMs, no existing pair chat, unique `(noteId, senderId)` → `CHAT_REQUEST_EXISTS`); `listForInbox(userId)` → `{ incoming: PENDING to me, outgoing: PENDING|DECLINED from me mapped to one state 'pending' }` with person, note excerpt (`lib/text-excerpt.ts`) and hub link; `accept(userId, id)`: recipient only, PENDING only; creates or reuses the DIRECT pair chat **without** the shared-group rule (extract the pair lookup + advisory-lock create of `getOrCreateDirectChat`, `message.service.ts` l.532-596, into an internal helper both use), posts the request text as the sender's first message, sets ACCEPTED + `conversationId` + `decidedAt`; `decline(userId, id)`: recipient only, sets DECLINED, nothing else.
- **K2-25** Inbox (`app/[locale]/(me)/messages`, `components/messages/`): a "Pieprasījumi" block at the top of `ConversationList`, rendered only when there are rows (so the `messages` baseline stays identical). Incoming row: avatar, name, "par ziņu „…“" (link to the note), their message (2 lines), Pieņemt (primary) / Noraidīt (quiet). Outgoing row: name, the note excerpt, "gaida apstiprinājumu" (forever after a decline, K-120). `components/messages/ChatRequestRow.tsx` (≤ 70). `?r=<id>` scrolls to an incoming request. `MessageService.unreadCount` adds incoming PENDING requests (the header badge shows them).
- **K2-26** Accept → the chat opens in the inbox (`?c=`), the request row goes; decline → the row goes for the recipient only. A request survives its note (expired or deleted): the row then shows no excerpt.

### 6.3 Ziņot — K2-27

Admin reports page (`app/[locale]/admin/reports/page.tsx`): note and reply reports show the text, author and a hub link, with "Dzēst" (K2-09) and "Atrisināt".

### 6.4 Notifications (K-87) — K2-28, K2-29

- **K2-28** New `NotificationPayload` types (union in `notification.service.ts` l.19, icons in `lib/notification-icons.ts`, text where the other types' texts live): `HUB_NOTE_REPLY` → the note's author when someone else replies (`{name}`, link `{noteHubHref}/messages?z={id}`, icon `MessageSquare`); `CHAT_REQUEST` → the recipient (`{name}`, link `/messages?r={id}`, icon `Mail`); `CHAT_REQUEST_ACCEPTED` → the sender (`{name}`, link `/messages?c={conversationId}`, icon `UserCheck`). - **K2-29** Email (R33): add the three types to `EMAIL_DIGEST_TYPES`; the digest already reads the bell headline, so nothing else changes. A notification whose note expired lands on `hub.notes.gone` (K2-12).

## 13. Risks

1. **Category cascade.** `HubNote.category` is `onDelete: Cascade`; tag merges (`taxonomy.service.ts` `mergePendingTag` l.484, `mergeL2` l.501, `bulkMerge` l.941) must move notes (`categoryId` → the canonical id) in the same transaction, or a merge deletes them.
2. **Limit race.** Without the advisory lock two tabs can post a 4th note; the lock key must be per author, not per hub.
3. **Request side channel.** Any difference for the sender between PENDING and DECLINED (a count, a sort, a cache tag, the "open" state appearing) breaks K-120; accept is the only event the sender sees.
4. **Reply reads.** Loading every note's replies with the page is the N×M trap; replies load with `?z=` or on first open (K2-21).
5. **`/messages` collision.** The hub page segment `messages` sits beside the site's `/[locale]/messages` inbox route; the hub path always has L1 and L2 before it, so no clash, but check `@panel` soft navigation board → hub Ziņas as in K1 Risk 1.
