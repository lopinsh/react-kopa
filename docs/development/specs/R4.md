**Defaults to confirm with the owner** (proposals; the plan and the ledger are silent):
1. **Online events only under "Visur".** A city filter leaves online events out and the city counts don't include them; they are counted once as `online` (AR-57 "shown under Visur"). Their stored city (the group's, by default) is kept for R10 and for the organiser, not for filtering.
2. **A multi-day event counts on one day** in the per-day counts: the day it starts, or the first day of the asked range if it began earlier (R5b lists it on that day too).
3. **The event's city comes from the approved list** plus the group's own city and the event's current city (either may still be waiting for approval); the event form does not suggest new cities (the group form does).
4. **The address stays required** (today's rule). With "Tiešsaistē" on, the same field is labelled "Saite" and takes the meeting link.
5. **Counts are for everyone:** members-only events are not in the cached counts; the per-day counts and the lists add the viewer's own members-only events, as the event list does today.

## 0. Motivation and design alignment

- **Service Law.** Every query lives in `lib/services/`: the where-builders and the count/day aggregation in one new module (`discovery-query.ts`, 2.1) used by both the lists and the counts, so a count can never disagree with its list. Services return typed objects; lists keep returning localized titles (`locale` in, `title` out); counts are keyed by slug and carry no titles (their `locale` only picks the search language): the names come from the taxonomy and city lists the page already loads.
- **Context Law.** The event form reads the group's city from `useGroupContext().city` (it renders inside the group layout), not from a prop; the city list comes from the existing `CitiesProvider` / `useCities()`.
- **Taxonomy Law.** Untouched: no colour work.
- **Defensive Coding.** The shared Zod schemas own the new rules (`lookingFor` trimmed, ≤ 60, empty → `null`; `city` required; `isOnline` boolean); forms keep their `isPending` guards and disable saving past the counter's limit, like the name.
- **Action Consistency.** No new action and no new error code: an unusable city answers `VALIDATION_FAILED` like the group form does; field messages live in the `wizard.*` / `eventWizard.*` namespaces like `NAME_TOO_LONG`. Actions keep revalidating with `updateTag('groups')` / `updateTag('events')`, which also refreshes the new caches.
- **Zero-Any / Constants.** `GROUP_LOOKING_FOR_MAX` next to `GROUP_NAME_MAX`; `DISCOVERY_EVENTS_MAX_LIMIT`, `DISCOVERY_DAY_RANGE_MAX` in `lib/constants`; Prisma-generated types only.
- **Expand → contract.** R4 only adds nullable or defaulted columns and an index; the deploy runs them while R3b serves. `NOT NULL` on `Event.city` is R5a's `require_event_city`, which may only run once R4 has been live on its own (build plan R5a card).

## 1. Data (the stop point)

`prisma/schema.prisma`:
```prisma
model Group {
  …
  /// "Ko meklējam?": one short line in the team's own words (one language, OD-12). Null when empty.
  lookingFor         String?        @db.VarChar(60)
  …
}

model Event {
  …
  /// The event's own place (AR-57): a `City.slug` like `Group.city`, no foreign key. Filled from the group's city.
  /// Nullable until R5a's `require_event_city` (old code may still create events without it during the R4 deploy).
  city              String?
  /// "Tiešsaistē": the event happens online; `location` then holds the link.
  isOnline          Boolean            @default(false)
  …
  @@index([city, startDate])
}
```

Two hand-written migration folders (they sort after the newest, `20261012120000_add_query_indexes_remove_unused_fields`):

**`prisma/migrations/20261014100000_add_group_looking_for/migration.sql`**
```sql
-- AlterTable
ALTER TABLE "Group" ADD COLUMN "lookingFor" VARCHAR(60);
```

**`prisma/migrations/20261014100100_add_event_city/migration.sql`**
```sql
-- AlterTable
ALTER TABLE "Event" ADD COLUMN "city" TEXT,
ADD COLUMN "isOnline" BOOLEAN NOT NULL DEFAULT false;

-- Every existing event takes its group's city (AR-57: "filled in with the group's city").
-- A group whose suggested city was rejected has '' (CityService.reject); its events get '' too, never NULL,
-- so R5a's NOT NULL step only has to re-fill events created by the old code during this deploy.
UPDATE "Event" AS e SET "city" = g."city" FROM "Group" AS g WHERE e."groupId" = g."id" AND e."city" IS NULL;

-- CreateIndex
CREATE INDEX "Event_city_startDate_idx" ON "Event"("city", "startDate");
```

Why this is safe while R3b serves: R3b's Prisma client lists its own columns, so it never reads the new ones; its `event.create` leaves `city` NULL and `isOnline` false (both allowed). `ADD COLUMN … DEFAULT false` is a metadata change on Postgres 15; the backfill touches each event row once. The NULL rows the old code may create between migrate and swap are covered by the read fallback in 2.1 and re-filled by R5a.

**Check (stop point):** `npm run db:generate`, `npx prisma migrate deploy` on the local DB (both apply, in order), then `npx prisma migrate dev --create-only --name drift_check` (dev server stopped) must answer that the schema is in sync and create nothing; if it creates a folder, the hand-written SQL differs from the schema: fix the SQL and delete that folder. Then in `psql` (or `npx prisma db execute`): `SELECT count(*) FROM "Event" WHERE "city" IS NULL` → 0; `SELECT count(*) FROM "Event" e JOIN "Group" g ON g.id = e."groupId" WHERE e.city <> g.city` → 0; `\d "Event"` shows `Event_city_startDate_idx`.

## 2. Services

### 2.1 `lib/services/discovery-query.ts` (new, ≤ 220 lines, no `next/cache`, no `next-intl`)

Plain Prisma functions shared by `DiscoveryService` and `EventService`. No caching here, so a throwaway script can call them (section 8). Exports:

```ts
/** Matches a group whose category or tags are this slug or sit under it (L1, L2 or L3; D10 for events). */
export function topicMatch(slug: string): Prisma.GroupWhereInput
/** The discovery group list's where (today's getGroups rules: PUBLIC unless type says PRIVATE, not hidden, ACTIVE non-wildcard category). */
export function groupWhere(filters: GroupDiscoveryFilters, lang: TextLang): Prisma.GroupWhereInput
/** The discovery event list's where, without the visibility part (callers add PUBLIC or the viewer's MEMBERS_ONLY). */
export function eventWhere(filters: EventDiscoveryFilters, now?: Date): Prisma.EventWhereInput
/** Facet rows for the counts: only the fields the aggregation needs. */
export function loadGroupFacetRows(input: FacetInput, lang: TextLang): Promise<FacetRow[]>
export function loadEventFacetRows(input: FacetInput, now?: Date): Promise<FacetRow[]>
/** Pure: the counts of DiscoveryCounts from rows (2.2 rules). */
export function aggregateFacets(rows: FacetRow[], input: FacetInput): Omit<DiscoveryCounts, 'kind'>
/** Pure: per-day counts in a time zone (Default 2). */
export function bucketByDay(rows: Array<{ startDate: Date }>, from: Date, to: Date, timeZone: string): DayCount[]
```
`FacetRow = { city: string | null; isOnline: boolean; l1Slug: string; tagSlugs: string[] }` where `tagSlugs` holds each tag's slug and, for an L3 tag, its L2 parent's slug (so an L2 counts groups tagged with it or any of its L3 children once). Internal, not exported from `lib/types`.

Rules the builders encode (moved, not re-invented: `DiscoveryService.getGroups` and `EventService.getDiscoverableEvents` lose their inline where code to these):
- **Several cities (D7).** `cities` empty or absent = "Visur" (no city condition). Groups: `city: { in: cities }`. Events: `isOnline: false` and `OR: [{ city: { in: cities } }, { city: null, group: { city: { in: cities } } }]`. The `city: null` branch is the deploy-window fallback; R5a deletes it with the `NOT NULL` step (say so in a comment naming R5a).
- **Topic.** `categoryId` (groups, today's id hierarchy match) and `category` (events, a slug of any level) and `tags` (slugs, any of them) all go through `topicMatch`: `OR` of the group's `category` and `tags` at the slug, its parent or its grandparent (the existing six-way `searchTags` match). Today the events' category filter only looks at the group's L1 category, so a sub-category slug finds nothing; through `topicMatch` it finds the groups tagged with it (D10).
- **Dates (D9).** With `from`/`to`: the event overlaps `[from, to)`: `startDate < to` and (`endDate >= from` or (`endDate` null and `startDate >= from`)). Without them: today's `status` rule (upcoming / past at the Latvian day boundary, `startOfTodayInRiga`). The span is clamped to `DISCOVERY_DAY_RANGE_MAX = 62` days (a month view plus its spill weeks); `from >= to` gives an empty result, not an error.
- **Search** stays as today (event text in any language, group name and description; groups also public sections and category titles).

### 2.2 Types (`lib/types/discovery.ts`)

Replace `DiscoveryFilters` (drop `city` and the single `tag`, and the stale "only supports single tag" TODO: `tags` works today):
```ts
export type DiscoveryKind = 'groups' | 'events';

export interface GroupDiscoveryFilters {
    /** City slugs; empty = Visur. */
    cities?: string[];
    categoryId?: string;
    /** Sub-category slugs (L2/L3); a group matches any of them. */
    tags?: string[];
    query?: string;
    type?: GroupType | string;
    take?: number;
    skip?: number;
}

export interface EventDiscoveryFilters {
    cities?: string[];
    /** A category slug of any level (L1, L2, L3). */
    category?: string;
    tags?: string[];
    search?: string;
    /** Ignored when `from`/`to` are set. Default 'upcoming'. */
    status?: 'upcoming' | 'past';
    from?: Date;
    to?: Date;
    /** Default DISCOVERY_EVENTS_LIMIT (100), clamped to 1…DISCOVERY_EVENTS_MAX_LIMIT (200). */
    limit?: number;
}

/** What the counts are asked for: the list's filters minus paging. */
export interface FacetInput {
    kind: DiscoveryKind;
    cities?: string[];
    /** The L1 whose sub-categories are counted (the drawer's open category). */
    l1Slug?: string;
    tags?: string[];
    query?: string;
    /** Events only. */
    from?: Date;
    to?: Date;
}

/** Counts keyed by slug; titles come from the taxonomy and city lists the page already has. */
export interface DiscoveryCounts {
    kind: DiscoveryKind;
    /** With every filter applied (= the list's total). */
    total: number;
    /** L1 slug → count; cities, query and dates applied, topic not (each facet ignores its own filter). */
    byCategory: Record<string, number>;
    /** L2/L3 slug → count inside `l1Slug`; cities, query, dates applied, tags not. `{}` without `l1Slug`. */
    bySubCategory: Record<string, number>;
    /** City slug → count; topic, query, dates applied, cities not; online events never here (Default 1). */
    byCity: Record<string, number>;
    /** Events only: online events matching topic, query and dates; 0 for groups. */
    online: number;
}

export interface DayCount {
    /** YYYY-MM-DD in the asked time zone. */
    day: string;
    count: number;
}
```
Each facet ignores only its own filter (the usual faceted-search rule: the Kur list shows how many you'd get per city with the chosen topic, the drawer shows how many per category in the chosen places). `total` applies everything. Cities and tags are sorted before they go into a cache key.

### 2.3 `DiscoveryService` (`lib/services/discovery.service.ts`)

```ts
getGroups(filters: GroupDiscoveryFilters, locale: string): Promise<{ groups: GroupCardData[]; hasMore: boolean; totalCount: number }>
getCounts(input: FacetInput, locale: string): Promise<DiscoveryCounts>
```
- `getGroups`: same behaviour, `cities` instead of `city`, where from `groupWhere`. Keep its `unstable_cache` (key already includes the where JSON).
- `getCounts` (new, D8): rows from `loadGroupFacetRows` / `loadEventFacetRows`, then `aggregateFacets`. `locale` only picks the search language for group category titles (no titles are returned). Rows are selected with the few fields `FacetRow` needs, so one query per call; on the seed DB a cold call must stay under 150 ms (measured in section 8). Leave a one-line comment: if a kind ever passes a few thousand rows, move the aggregation into SQL.

**Caching (D8).** This version documents `use cache` + `cacheTag` as the successor of `unstable_cache`, but only under the site-wide `cacheComponents` switch (`node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-cache.md`), which this app has not turned on and which would change every dynamic page. So R4 stays with `unstable_cache` like the 16 existing callers (still supported in 16.4: `…/04-functions/unstable_cache.md`):
- `unstable_cache(fn, ['discovery-counts-v1', kind, sortedCities, l1Slug, sortedTags, fromIso, toIso, todayRigaIso], { tags: ['groups', 'events', 'categories'], revalidate: 300 })`. `todayRigaIso` (the Latvian day) is in the key for events so "upcoming" rolls over at midnight.
- With a search word (`query`) the counts are not cached (unbounded keys); they run directly.
- **Invalidation:** the existing actions already call `updateTag('groups')` (group create, update, delete, leave, kick, approve, hide/restore via moderation) and `updateTag('events')` (event create, update, delete, moderation), and `revalidateTag('categories', 'max')` (taxonomy changes); `updateTag` gives read-your-own-writes inside the acting Server Action (`…/04-functions/updateTag.md`). Grep that no group or event mutation lacks its tag (`updateGroup` has it; check `transferOwnership` needs none). Attendance changes don't touch counts.

Also in this file: `searchContextual`'s event subtitle becomes `e.isOnline ? tEvent('online') : (e.location || cityLabel(tCities, e.city ?? e.group.city))` (one-line, trivially correct).

## 8. Checking the queries without UI (no debt)

A throwaway script, never committed: copy the block below to `tmp-r4-check.ts` at the repo root (git-ignored by `/tmp-*`), run `npx tsx --env-file=.env tmp-r4-check.ts`, then delete it before committing (it would otherwise be type-checked). ```ts
import { prisma } from './lib/prisma';
import { groupWhere, eventWhere, loadGroupFacetRows, loadEventFacetRows, aggregateFacets, bucketByDay } from './lib/services/discovery-query';

const time = async <T>(label: string, fn: () => Promise<T>) => { const t = performance.now(); const r = await fn(); console.log(label, Math.round(performance.now() - t), 'ms'); return r; };

async function main() {
    // D7: one city vs two, groups and events; the union of two singles equals the pair.
    const g1 = await prisma.group.count({ where: groupWhere({ cities: ['Riga'] }, 'lv') });
    const g2 = await prisma.group.count({ where: groupWhere({ cities: ['Jurmala'] }, 'lv') });
    const g12 = await prisma.group.count({ where: groupWhere({ cities: ['Riga', 'Jurmala'] }, 'lv') });
    console.log('D7 groups', g1, g2, g12, g1 + g2 === g12 ? 'OK' : 'MISMATCH');
    const eJ = await prisma.event.findMany({ where: { AND: [eventWhere({ cities: ['Jurmala'] }), { visibility: 'PUBLIC' }] }, select: { slug: true, city: true, isOnline: true } });
    console.log('D7 events in Jurmala (expect the Ķemeri walk of a Rīga group):', eJ);
    // Default 1: online events only under Visur.
    const online = await prisma.event.count({ where: { AND: [eventWhere({}), { isOnline: true }] } });
    const onlineInRiga = await prisma.event.count({ where: { AND: [eventWhere({ cities: ['Riga'] }), { isOnline: true }] } });
    console.log('online under Visur', online, 'under Riga', onlineInRiga, onlineInRiga === 0 ? 'OK' : 'WRONG');
    // D8: counts; total equals the list's count; each facet ignores its own filter.
    for (const kind of ['groups', 'events'] as const) {
        const input = { kind, cities: ['Riga'] };
        const rows = await time(`D8 ${kind} rows`, () => kind === 'groups' ? loadGroupFacetRows(input, 'lv') : loadEventFacetRows(input));
        console.log(kind, aggregateFacets(rows, input));
    }
    // D9: a 14-day range from today, per day in Riga time; sum equals the range count.
    const from = new Date(); from.setHours(0, 0, 0, 0); const to = new Date(from.getTime() + 14 * 864e5);
    const inRange = await prisma.event.findMany({ where: { AND: [eventWhere({ from, to }), { visibility: 'PUBLIC' }] }, select: { startDate: true } });
    const days = bucketByDay(inRange, from, to, 'Europe/Riga');
    console.log('D9', days, days.reduce((s, d) => s + d.count, 0) === inRange.length ? 'OK' : 'MISMATCH');
    // D10: a sub-category slug finds events through the group's tags (pick a tag the seed uses).
    const tag = await prisma.category.findFirst({ where: { level: { in: [2, 3] }, groupsWithTags: { some: { events: { some: {} } } } }, select: { slug: true } });
    if (tag) console.log('D10', tag.slug, await prisma.event.count({ where: eventWhere({ category: tag.slug }) }), '> 0 expected');
    // Index: usable for a city + date range (the planner may prefer a seq scan on seed-sized tables).
    await prisma.$executeRawUnsafe('SET enable_seqscan = off');
    console.log(await prisma.$queryRawUnsafe(`EXPLAIN SELECT id FROM "Event" WHERE city IN ('Riga','Jurmala') AND "startDate" >= now() ORDER BY "startDate" LIMIT 25`));
}
main().finally(() => prisma.$disconnect());

## 11. Risks

- **The deploy window.** R3b serves after the migrations and creates events with `city` NULL; R4 reads them through the group-city fallback and its edit form fills the city; R5a re-fills and sets `NOT NULL`. Never push R4 and R5a together (plan, R5a card).
- **Count cost.** `getCounts` reads one narrow row per matching group or event; cached for 5 minutes per filter set and invalidated by the existing tags. Uncached with a search word. Measured in 8; R5a measures again on the real page.
- **Faceted semantics.** Each facet ignores its own filter (2.2); R5a must show the same numbers the lists then return (the reviewer clicks a count and compares with the list total in R5a).
- **Cities that change.** A rejected pending city empties events and groups alike (`''`); an approved one keeps its slug. A group moving city does not move its events (each event has its own place, AR-57).
- **Per-day counts and time zones.** Days are cut in the asked zone (`tz` cookie in R5b), DST weeks included; "past" stays the Latvian-day rule. R5b's review checks a week across the October DST change.
- **The events' category filter changes meaning:** a sub-category now finds events through the group's tags (D10). Before, it silently found nothing; nothing relied on that.
