# R33 E-pasts

Owner-approved design (29 Oct): people who are away hear by email that something waits for them on the site, as one short digest of unread things, never the content itself. No drawing; the one UI change is a switch in Iestatījumi (design.md row "Me", R9c), plus a small unsubscribe page. Two sessions: **R33-1** (schema, locale, opt-out) and **R33-2** (mailer, digest, cron route). One additive migration, in R33-1.

## Goal

Every 5 minutes the home server's cron POSTs `/api/cron/email-digest`. For each person with unread direct messages or unread "you must act / you got an answer" notifications that are at least 10 minutes old and not yet emailed, the site sends one email: "N new things on Ejam Kopā", one line per item, one button to the site. LV or EN by the person's last used language. One switch in Iestatījumi and a signed link in every email turn it off.

## Invariants

- **No content in mail.** A line is a bell headline (`notifications.headline.<TYPE>`, which carries at most a person's name) plus the group name or event title; a message line names only the sender. Never `excerpt`, `reason`, message `content`, or the `detail` of `formatNotificationText` (`lib/utils/notification-text.ts:21`).
- **Service Law.** All Prisma access for the digest lives in `lib/services/email-digest.service.ts` (plus the two helpers added to `message.service.ts` and `notification.service.ts`). The route handler only checks the secret and calls the service; it returns JSON counts, never user data.
- **Unread means what the app means.** Messages: the `unreadCount` definition (`message.service.ts:380`, `accessWhere` `:92`, `newestFromOthers` `:120`), so GROUP chats reach the contact person and the group's current OWNER/ADMIN team. Notifications: `audience = 'USER'`, `read = false`. Reading in the app within 10 minutes means no email.
- **Once per item.** A notification is emailed at most once (`Notification.emailedAt`); a chat is emailed again only when someone writes after the last digest (`User.messagesEmailedAt`).
- **Never mail** a user with `email = null`, an `@DEMO_EMAIL_DOMAIN` address (`lib/constants/vitality.ts:2`), or `emailNotifications = false`.
- **No first-deploy blast.** Only items created within the last 24 h count (`EMAIL_DIGEST_LOOKBACK_MS`), so old unread notifications from before R33 never go out.
- **Safe without setup.** `SMTP_URL` unset: the email is logged (`console.info`, recipient id, subject, text body) and counted as sent. `CRON_SECRET` unset: the route answers 404, like the feedback API (`lib/feedback/api-token.ts`).
- Additive migration only (expand); the running old app ignores the four columns.
- No visual baseline changes (see Visual baseline).

## Constants (R33-1)

New `lib/constants/email.ts`, re-exported from `lib/constants/index.ts`:

```ts
export const EMAIL_DIGEST_DELAY_MS = 10 * 60_000;       // an item waits this long before it may be mailed
export const EMAIL_DIGEST_LOOKBACK_MS = 24 * 60 * 60_000; // older items never trigger mail
export const EMAIL_DIGEST_MAX_LINES = 10;                // more become "and N more"
export const EMAIL_DIGEST_MAX_USERS = 200;               // per cron run; the rest go in the next run
export const EMAIL_DIGEST_TYPES = [
  'JOIN_REQUEST', 'APPLICATION_RECEIVED', 'INQUIRY_RECEIVED', 'APPLICATION_INQUIRY',
  'REQUEST_APPROVED', 'APPLICATION_ACCEPTED', 'APPLICATION_DECLINED',
  'EVENT_REQUEST', 'EVENT_APPROVED', 'EVENT_DECLINED', 'EVENT_LET_IN',
] as const;
```

The type list is picked from `NotificationPayload['type']` (`notification.service.ts:20`): requests, applications, inquiries, approvals, accepts, let-ins and declines. Left bell-only: `NEW_POST`, `NEW_EVENT`, the waitlist broadcasts (`EVENT_SPOT_FREED`, `EVENT_ROOM_AGAIN`, `EVENT_NOW_OPEN`: sent to many at once, stale in minutes), removals and cancellations, moderation and role notices, cities and tags (see Owner questions 1). Type the constant as `readonly NotificationPayload['type'][]` via `satisfies` so a renamed type fails tsc (import the type with `import type`).

## Unsubscribe (R33-1)

Signed link, no sign-in needed. Built now so R33-2 only calls it.

- `lib/email/unsubscribe-token.ts` (no Prisma): `signUnsubscribe(userId): string` = base64url HMAC-SHA256 of `unsubscribe:${userId}` with `AUTH_SECRET` (`node:crypto` `createHmac`); `verifyUnsubscribe(userId, sig): boolean` with `timingSafeEqual` on equal-length buffers (pattern: `lib/feedback/api-token.ts:1`). No expiry (an old email's link must still work); rotating `AUTH_SECRET` voids old links, which is accepted.
- `unsubscribeUrl(userId, locale)` = `${NEXT_PUBLIC_APP_URL}/${locale}/email/unsubscribe?u=<id>&s=<sig>`; `unsubscribePostUrl(userId)` = `${NEXT_PUBLIC_APP_URL}/api/email/unsubscribe?u=<id>&s=<sig>`.
- **Page** `app/[locale]/email/unsubscribe/page.tsx` (server, `max-w-focus`, `PageHead`): a valid pair shows the title, one sentence and a form button "Atteikties" (a client `UnsubscribeButton` calling the action, guarded by `isPending`), then the done state with a link to Iestatījumi. An invalid pair shows `invalid`. GET never changes anything (mail scanners open links).
- **Action** `unsubscribeByLink({ u, s })` in `actions/email-actions.ts`: verify, then `UserService.updateEmailSettings(u, { emailNotifications: false })`; `NOT_FOUND` for a bad pair (no difference between unknown user and bad signature). Zod schema `unsubscribeLinkSchema` in `lib/validations/email.ts`.
- **One-click route** `app/api/email/unsubscribe/route.ts`, `POST` only (RFC 8058: mail clients POST `List-Unsubscribe=One-Click` to the header URL): verify `u`/`s` from the query, set `emailNotifications = false` through the service, answer `200` with an empty body; a bad pair also answers `200` (no oracle). `/api` is outside the proxy matcher, so no locale or onboarding redirect interferes.
- `noindex` on the page (`robots: { index: false }` in `generateMetadata`).

## Digest service (R33-2)

`lib/services/email-digest.service.ts`, `EmailDigestService.run(now = new Date()): Promise<{ users: number; sent: number; logged: number; failed: number; skipped: boolean }>`.

1. **One run at a time.** `SELECT pg_try_advisory_lock(33033)` via `prisma.$queryRaw`; false → return `{ skipped: true, ... }`. Release with `pg_advisory_unlock` in `finally`. Use one interactive connection for lock and unlock (`prisma.$transaction` with a generous `timeout`, or lock and unlock on the same `$queryRaw` session); if Prisma's pool makes that unreliable, use `pg_try_advisory_xact_lock` inside a transaction that only guards the candidate claim (step 4). Builder picks one and states it in the code comment.
2. **Window.** `cutoff = now - EMAIL_DIGEST_DELAY_MS`, `since = now - EMAIL_DIGEST_LOOKBACK_MS`.
3. **Candidates** (user ids, union, at most `EMAIL_DIGEST_MAX_USERS`, oldest item first):
   - Notifications: `notification.findMany({ where: { audience: 'USER', read: false, emailedAt: null, type: { in: EMAIL_DIGEST_TYPES }, createdAt: { gte: since, lte: cutoff } }, distinct: ['userId'], select: { userId: true } })`. Add as `NotificationService.digestCandidates(since, cutoff)`.
   - Messages: `MessageService.digestRecipients(since, cutoff)`: conversations with a message in `[since, cutoff]`; recipients = DIRECT participants, GROUP `contactUserId` plus `teamUserIds(originGroupId)` (`message.service.ts:103`), each minus the sender of that message. Reuse the module's helpers; export nothing Prisma-shaped.
   - Then filter users: `emailNotifications: true`, `email: { not: null }`, `NOT: { email: { endsWith: '@' + DEMO_EMAIL_DOMAIN } }`.
4. **Per user** (sequentially; prototype volume):
   - Messages: `MessageService.unreadForDigest(userId, since, after)` with `after = max(user.messagesEmailedAt, since)`: conversations in `accessWhere(userId)` whose newest message from others (`newestFromOthers`) is `> max(lastReadAt, after)`. Returns `[{ conversationId, senderName, newestAt }]` (sender = that newest message's sender, `name ?? username`). An email is due only if at least one item (message or notification) has `createdAt <= cutoff`; younger items ride along in the same email.
   - Notifications: unread, `emailedAt: null`, the types, `createdAt >= since`, `orderBy createdAt desc`. Fold like the bell (same type and link = one line, `groupUnread` logic `notification.service.ts:42`; reuse it by exporting a pure helper, not by copying).
   - Nothing due → next user. Otherwise build the email (below), `sendMail`, then in one `updateMany`/`update`: `Notification.emailedAt = now` for every listed id (folded ones included), `User.messagesEmailedAt = now` if any message line. Send first, mark after: a crash between the two can send one duplicate, never lose one.
   - A send error: `console.error` with the user id, count `failed`, leave unmarked (retried in 5 min). Three consecutive failures are not tracked; see Risks.
5. Return the counts.

The service resolves texts with `getTranslations({ locale: user.locale ?? DEFAULT_LOCALE, namespace })` from `next-intl/server` (explicit locale; works in a route handler). If `formatNotificationText`'s translator type (`useTranslations<'notifications'>`) does not accept the server translator, widen its parameter type to a minimal interface; do not cast with `as any`.

## Email (R33-2)

Light only, system font stack, the brand accent as a literal hex taken from `app/globals.css` default theme in one constant, no images, no tracking pixel, no external assets. Escape every interpolated string (names and titles are user text): a small `escapeHtml` in the same file.

- Headers: `List-Unsubscribe: <unsubscribePostUrl>`, `List-Unsubscribe-Post: List-Unsubscribe=One-Click`.

## Acceptance

R33-1:
- `prisma migrate deploy` applies; the old build still runs against the new schema.
- Sign in, switch language to EN, wait for the daily write (or set `"lastSeenAt" = now() - interval '2 days'` and reload): `User.locale = 'en'`. A garbage `NEXT_LOCALE` cookie writes nothing.
- Iestatījumi: E-pasts block between Privātums and Izskats; switch saves on change, survives reload, toast and revert on failure (stop the DB). A demo user (`@demo.ejam.invalid`) sees it disabled with the no-email line. Privātums switches behave as before.
- Unsubscribe: generate a link in a node one-liner (`signUnsubscribe`), open it signed out: page, button, done state, `emailNotifications = false`. A changed `s` shows `invalid` and changes nothing. GET alone changes nothing. `curl -X POST '<api url>'` with a valid pair turns it off and answers 200; a bad pair answers 200 and changes nothing.
- LV and EN; 360 / 768 / 1280 / 1920; light and dark for Iestatījumi and the unsubscribe page.

R33-2 (local, `SMTP_URL` unset, `CRON_SECRET` set):
- No header or a wrong one: 401; `CRON_SECRET` empty: 404; GET: 405.
- Make user A (seeded, real-looking address, not demo) receive a message from B and a `JOIN_REQUEST`; backdate both 11 minutes (`UPDATE ... SET "createdAt" = now() - interval '11 minutes'`). POST: response `{ users: 1, logged: 1 }`; the log shows A's subject "2 jaunas lietas Ejam Kopā" (or EN when `locale = 'en'`), the sender's name, the headline with the group name, and no message text or request excerpt. `emailedAt` and `messagesEmailedAt` set.
- POST again: nothing for A. B writes again: next run lists the chat again. A reads the chat in the app first: no line for it.
- Items 5 minutes old: nothing. An item 11 minutes old plus one 2 minutes old: one email with both.

## Risks

- **Spam folder / blocked sender.** Without SPF, DKIM and DMARC on the `MAIL_FROM` domain mail lands in spam. Owner setup, non-blocking; the feature is inert until then.
- **Repeated failures.** A broken SMTP config retries every 5 minutes for 24 h per item, logging each time. Acceptable at prototype size; the logs show it.
- **Duplicate on crash.** Send-then-mark can send one duplicate if the process dies between them. Chosen over losing an email.
- **Locale lag.** Language follows the daily write, so a switch takes up to a day to reach emails.
- **Cron on the home server.** If "media" is down, digests pause; nothing is lost within the 24 h lookback.
