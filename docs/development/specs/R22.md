Spec for release R22 (drawings: `docs/development/r22-type-system.html`, `r23-admin-drawer.html`; context only, nothing here is built from a drawing). Written 23 Oct 2026 against `main` at `7180cfd`. Owner approved the split below.

| R22-2 | The "Burti" page in Admin > Dizains (base, contrast, heading weight, leading, tag case, per-role overrides, live sample) | next |

## 0. Goal (R22-1)

An admin will later tune the site's type (R22-2). R22-1 builds the foundation that makes that safe: a sparse, versioned `type` value stored on `SiteTheme`, validated by one Zod schema, carried through draft, publish and reset, and turned into CSS variables on the server (Taxonomy Law: first paint is right). The type utilities in `app/globals.css` read those variables with today's literals as fallbacks. With no `type` stored, the page is byte-for-byte what it is today.

**Design alignment.** Service Law (all Prisma in `ThemeService`), Constants Law (fonts' weights and the role registry in `lib/constants`), Defensive Coding (one shared schema, validated again on the server), Taxonomy Law (variables emitted in the layout `<style>`, never resolved on the client).

## Invariants (the reviewer checks each)

1. **Zero visual diff.** `npm run test:visual` passes with `maxDiffPixels: 0` and no baseline touched. No screen is listed to change.
2. **Unset emits nothing.** A theme without `type`, or with `type: {v:1}`, produces exactly today's `themeCss` output (compare the string before and after for all 5 presets x 3 styles in a throwaway script; not committed).
3. **Fallbacks are today's literals.** Every `var(--type-<role>-…, <literal>)` fallback equals the value currently in `app/globals.css`, character for character.
4. **Old rows and old caches work.** A `SiteTheme` row with `type` null, and a cached `ThemeContext` without `type`, render as today (the cache tag is `site-theme-published`; `type` is optional everywhere).
5. **Migration is additive** (nullable column), so the running version is unaffected during deploy.
6. **No admin UI, no new i18n keys, no new routes.**
7. **Nothing under 11 px** and heading line-height never below 1.05, whatever is stored.
8. Only validated, numeric or enum values reach the `<style>` text (no string from the DB is interpolated unvalidated).

## 2. Constants (R22-1 commit 2)

### 2.1 `lib/constants/theme.ts`: `weights` on `THEME_FONTS`

Extend the `satisfies` shape with `weights: readonly number[]` and set (matching `lib/theme-fonts.ts`):

| Font | weights |
|---|---|
| geist, literata, commissioner, source-serif, lora, nunito-sans, raleway (variable) | `[400, 500, 600, 700]` |
| atkinson | `[400, 700]` |
| alegreya-sans | `[400, 500, 700, 800]` |
| archivo-black | `[400]` (keeps its existing `weight: 400`, which still wins for headings) |

Add a helper `snapWeight(fontId, weight)` (in `lib/constants/theme.ts`, pure): the nearest weight the font has, ties go up. Variable fonts accept any 400-700 in CSS, but the allowed set is the four listed above so the picker later has steps.

### 2.2 `lib/constants/type-roles.ts` (new, export through `lib/constants/index.ts`)

`TYPE_ROLES`: 11 entries, `{ id, utility, heading, size, line, weight, tracking }`. `heading: true` for display, title, section, item. Values are today's, from `app/globals.css`:

| id | utility | heading | size (min / fluid / max) | line | weight | tracking |
|---|---|---|---|---|---|---|
| display | `text-display` | yes | 2rem / 1.55rem + 2vw / 3.25rem | 1.05 | style's | -0.02em |
| title | `text-title` | yes | 1.625rem / 1.4rem + 1vw / 2.25rem | 1.1 | style's | -0.015em |
| section | `text-section` | yes | 1.25rem / 1.15rem + 0.45vw / 1.5rem | 1.2 | style's | -0.01em |
| item | `text-item` | yes | 1.0625rem / 1rem + 0.2vw / 1.1875rem | 1.3 | style's | normal |
| body | `text-body` | no | 1rem | 1.6 | 400 | normal |
| body-sm | `text-body-sm` | no | 0.9375rem | 1.5 | 400 | normal |
| button | `text-button` | no | 0.9375rem | 1.2 | 500 | normal |
| button-sm | `text-button-sm` | no | 0.875rem | 1.2 | 500 | normal |
| meta | `text-meta` | no | 0.8125rem | 1.45 | 400 | normal |
| tag | `text-tag` | no | 0.75rem | 1.2 | 600 | 0.02em |
| human-note | `human-note` | no | 0.875rem | inherit | inherit | normal |

Export `TYPE_ROLE_IDS` (tuple, for the Zod enum) and `type TypeRoleId`. `weight: null` for heading roles and human-note means "no default from the registry" (heading roles read `--heading-weight`; human-note inherits). The registry is the single source for the later R22-2 UI and for the CSS in 4.

## 3. Validation (R22-1 commit 2)

`lib/validations/theme.ts`: add and export `themeTypeSchema` and `type ThemeType`, and `type: themeTypeSchema.optional()` on `themeInputSchema`.

```ts
export const themeTypeSchema = z.object({
    v: z.literal(1),
    base: z.number().min(15).max(17).multipleOf(0.5).optional(),          // body px
    contrast: z.number().min(0.8).max(1.25).optional(),                    // spread between heading and body sizes
    headingWeight: z.number().int().min(400).max(900).optional(),          // snapped to the heading font at render
    leading: z.enum(['compact', 'normal', 'airy']).optional(),             // text roles only
    tagCase: z.enum(['none', 'upper']).optional(),
    roles: z.partialRecord(z.enum(TYPE_ROLE_IDS), z.object({
        min: z.number().min(11).max(80).optional(),                        // px
        max: z.number().min(11).max(80).optional(),
        size: z.number().min(11).max(80).optional(),                       // px, fixed size (non-fluid roles, or flattens a fluid one)
        weight: z.number().int().min(400).max(900).optional(),
        font: z.enum(['heading', 'body']).optional(),
    }).refine((r) => r.min === undefined || r.max === undefined || r.min <= r.max)).optional(),
});
```

Floating-point: `multipleOf(0.5)` is exact for halves. Use `.strict()` is NOT used (a later version may add keys; unknown keys are stripped). A stored row that fails the schema is treated as no `type` (see 5), never as a failed theme.

## 4. CSS (R22-1 commit 3)

### 4.1 `app/globals.css`: the type utilities

Rewrite the 11 utilities so each property reads `var(--type-<id>-<prop>, <today's literal>)`. Properties: `size` -> `font-size`, `line` -> `line-height`, `weight` -> `font-weight`, `font` -> `font-family`, `tracking` -> `letter-spacing`. Examples of the pattern:

- `text-display`: `font-family: var(--type-display-font, var(--font-heading)), system-ui, sans-serif; font-weight: var(--type-display-weight, var(--heading-weight)); font-size: var(--type-display-size, clamp(2rem, 1.55rem + 2vw, 3.25rem)); line-height: var(--type-display-line, 1.05); letter-spacing: var(--type-display-tracking, -0.02em);` Keep `font-synthesis-weight: none` and the `text-wrap-style: balance` line and its comment.
- Text roles (body, body-sm, button, button-sm, meta, tag) have no `font-family` today: add none by default, but `--type-<id>-font` (when set) must apply, so declare `font-family: var(--type-<id>-font, inherit)`. `inherit` equals the computed value they have now (body font, via `body` and preflight's `font: inherit` on controls). Verify with the visual run; if `inherit` shifts any control, use `font-family: var(--type-<id>-font, var(--font-sans)), system-ui, sans-serif` instead.
- `human-note`: size `var(--type-human-note-size, 0.875rem)`, line `var(--type-human-note-line, inherit)`, weight `var(--type-human-note-weight, inherit)`, font `var(--type-human-note-font, inherit)`; keep `font-style: italic` and `color: var(--primary)`.
- Fallback for tracking on roles without one: `normal`.

Update the comment above the roles: "Type roles read `--type-<role>-*` (set by the theme, `lib/theme/css.ts`), falling back to the literals here." Do not touch `weight-medium`, `weight-strong`, `PageHead`, or any component.

### 4.2 `lib/theme/css.ts`: `themeTypeVars(type, headingFont, bodyFont)`

New pure function in a new file `lib/theme/type-vars.ts` (keep `css.ts` under control; `css.ts` imports it). Returns `Record<string,string>`; **only keys derived from set values are returned**; `undefined` or `{v:1}` returns `{}`.

Rules, in this order:

1. **base** (px B, set): every text role's size is `today * B/16`, in rem, rounded to 0.0625rem steps (1 px). Heading roles scale with it as well (their min, fluid intercept and max rem values are multiplied; the vw slope is left alone). Emit `--type-<id>-size`.
2. **contrast** (C, set): heading roles' sizes move away from the body size by C: `size' = bodySize + (size - bodySize) * C` applied to min and max (and to the intercept; slope scales by C). Text roles are unaffected. With C = 1 the result equals base-scaled sizes.
3. **leading** (set): text roles only (body, body-sm, meta, tag, human-note excluded from fixed-ratio: they all get it) multiply today's line by `compact 0.9`, `normal 1` (emit nothing), `airy 1.1`; button and button-sm are single-line controls and are left alone. Heading roles keep their own lines, but any heading line in the output is clamped to at least 1.05.
4. **headingWeight** (set): emit `--heading-weight` (overrides the style's, which sits earlier in the same block, so put it after `themeStyleVars`), snapped with `snapWeight(headingFont, …)`. If the heading font has a fixed `weight` (Archivo Black) emit nothing: the font wins as today. Unset: nothing (style's weight stays).
5. **tagCase** `upper`: emit `--type-tag-transform: uppercase` and give `text-tag` `text-transform: var(--type-tag-transform, none)`. When uppercase, tag tracking becomes `0.06em` (`--type-tag-tracking`) unless the role override sets size; this is the one coupled default. `none` or unset emits nothing.
6. **roles overrides**, applied last, win over 1-5 for the same role and property:
   - `min`/`max` on a fluid role: rebuild `clamp(min, <fluid middle>, max)` from the registry's middle with the new min/max (px to rem, /16); if only one is given, the other is the (scaled) default.
   - `size` (px): `--type-<id>-size: <size/16>rem`, a fixed size, replacing the clamp.
   - `weight`: `--type-<id>-weight`, snapped to the font the role uses (heading roles: `headingFont`, text roles: `bodyFont`, or the role's own `font` override).
   - `font`: `--type-<id>-font: var(--font-heading)` for `heading`, `var(--font-sans)` for `body`.
7. **Floors**: every emitted size (px) is clamped to at least 11; a clamp's min is at least 11 px and its max at least its min. Round rem to 4 decimals.

`themeCss(def)` gets `def.type?` (add `type?: ThemeType` to `ThemeDefinition`) and spreads `themeTypeVars(...)` into the `html:root` block, last. The editor sample (`themeSampleVars`) does **not** take `type` in R22-1 (R22-2 does); note this in a code comment on `themeSampleVars`.

## 5. Service, action and hook (R22-1 commit 4)

Both branches (preset and custom) return `type`. `presetInput` has no `type` (reset publishes without it, which stores `Prisma.JsonNull`/absent: write `type: parsed.data.type ?? Row type in the mapper gains `type?: Prisma.JsonValue | null`.
- `actions/theme-actions.ts`: no new action. The existing actions already parse through `themeInputSchema`; confirm `type` survives (add to the explicit object if the action rebuilds the input field by field; `grep -n "styleKey" actions/theme-actions.ts` showed no field-by-field copy, so likely nothing to do).

## 10. Risks

- **`inherit` fallbacks on controls** may differ from today's font on `button`/`input` elements; mitigated by the visual run and the alternative in 4.1.
- **Heading weight cascade**: `--heading-weight` is emitted by `themeStyleVars` and again by `themeTypeVars`; the later key in the same block wins only if the spread order is style, then type. Test it.
- **Prisma Json null**: writing `undefined` leaves the old value on update; here rows are created fresh, so `Prisma.JsonNull` is only needed for an explicit null. Verify the type compiles (`InputJsonValue | NullableJsonNullValueInput`).
- **Fluid maths**: contrast and base operate on rem; the slope in `vw` is not scaled by base (only by contrast) so large screens grow less than small ones. Fine for R22-1 (nothing uses it yet); R22-2 judges it visually.
- **Cache**: the layout reads a cached published theme; an old cache lacks `type`, which is valid. Publishing already expires the tag.

## 13. Owner questions (the builder uses the default unless the owner objects)

1. **Uppercase tags also widen tracking to 0.06em?** Default: yes (uppercase at 0.02em looks cramped); the override of tag tracking is not offered in R22-2.
